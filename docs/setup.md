# First-run setup

This page takes a new install from an empty checkout to a working app: generate the secrets, set up login, start the stack, and finish the setup wizard at the app's `/setup`. [docs/login.md](login.md) has the details of each login mode.

For a host with no internet, [docs/offline.md](offline.md) adds the steps to build and move the images, run a local Ollama server, and check that nothing calls out.

## 1. Generate `.env`

```sh
scripts/init-env.sh --auth-mode oidc
```

The script needs a POSIX shell and `openssl`. It copies `.env.example` to `.env` and sets new random values for:

- `KEY_ENCRYPTION_KEY`, which encrypts saved provider keys
- `SESSION_SECRET`, which seals the frontend's session cookies
- `POCKET_ID_ENCRYPTION_KEY`, which encrypts Pocket ID's data
- `POSTGRES_PASSWORD`, and a `DATABASE_URL` that uses it

It prints the names it set but never the values. It also prints the settings the mode still needs and the next steps. `.env` is readable only by you (mode 600).

`--auth-mode` takes `oidc`, `firebase`, or `demo`. It sets `AUTH_MODE` only when `AUTH_MODE` is empty.

**Keep a copy of `KEY_ENCRYPTION_KEY`** somewhere safe, apart from this machine. Saved provider keys cannot be read without it, and a new key cannot recover them.

The script never changes a value that is set, so you can run it again at any time:

- On an existing `.env`, it fills only the empty values among `KEY_ENCRYPTION_KEY`, `SESSION_SECRET`, and `POCKET_ID_ENCRYPTION_KEY`.
- It leaves `POSTGRES_PASSWORD` and `DATABASE_URL` as they are, even when they are empty, because the database in `.data/postgres` may already use them.
- When `.env` is missing but `.data/postgres` already holds a database, that database was set up with the default password `focus_funnel`, since `docker compose up` works without `.env`. The script then keeps `focus_funnel` and prints how to change the password inside Postgres first.

Connector tokens (with `MCP_ENABLED=true`) are not generated by the script, because they come from each connected service. Put each one in `.env` under the name that its connector's `auth.env` gives in `connectors.yaml`. The script reminds you of this when `MCP_ENABLED=true`. [docs/connectors.md](connectors.md) explains connectors, `connectors.yaml`, and the Google Calendar example.

## 2. Use the same compose files for every command

The Pocket ID overlay and the offline overlay change what the backend sees, such as `OIDC_INTERNAL_URL`. Every `docker compose` command for one install should use the same `-f` files, including `logs`, `restart`, and the doctor. The simplest way is to name the files once in `.env`:

```sh
COMPOSE_FILE=docker-compose.yml:docker-compose.pocket-id.yml
```

Compose reads `COMPOSE_FILE` from `.env`, so `docker compose up`, `docker compose logs backend`, and the rest then use both files without `-f`. On Windows, separate the files with `;` instead of `:`. The commands below spell out the `-f` files so they work either way.

## 3. Set up login before the first full start

Both servers refuse to start until the login settings are complete. The wizard shows these settings but cannot change them.

With Pocket ID, start it on its own first, then register Focus Funnel as a client:

```sh
docker compose -f docker-compose.yml -f docker-compose.pocket-id.yml up -d pocket-id
```

Then follow [Pocket ID in docs/login.md](login.md#pocket-id) from step 4: create the Pocket ID admin at http://localhost:1411/setup (that is Pocket ID's own setup page, not the app's), add a passkey, add the client, and copy its values into `.env`:

```sh
OIDC_ISSUER=http://localhost:1411
OIDC_CLIENT_ID=<client id>
OIDC_CLIENT_SECRET=<client secret>
```

For another OpenID Connect provider or Firebase, fill in the settings that [docs/login.md](login.md) lists for it. Also set `AUTH_ALLOWED_EMAILS` if only some accounts should get in (see [Allow-list](login.md#allow-list)). Without it, anyone your login provider lets in can use the instance.

## 4. Start and find the setup token

```sh
docker compose -f docker-compose.yml -f docker-compose.pocket-id.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.pocket-id.yml logs backend | grep -A2 'Setup token'
```

The backend applies the database migrations, and then, while setup is open, prints:

```
Focus Funnel setup is open.
Setup token: 3q9X...
Open http://localhost:3000/setup (the app's /setup, not Pocket ID's), log in, and enter this token.
A new token is printed each time the backend starts, until setup is finished.
```

The token proves that the person finishing setup can read the server's log. Each start prints a new token, and an older one stops working. If you lost it, restart the backend and read the log again:

```sh
docker compose -f docker-compose.yml -f docker-compose.pocket-id.yml restart backend
```

Run one backend process. Each process would print its own token, and only the last one printed would work.

## 5. The setup wizard

Open the app's `/setup` (http://localhost:3000/setup by default), log in, and enter the token. The token is kept in that browser tab only. The wizard has four steps. Each step lists its items with a state (OK, missing, failed, warning, or info) and the settings that control them.

1. **Login** shows the mode, the issuer and client ID (or the Firebase project), and the allow-list entries, or "none set". These come from `.env`. To change them, edit `.env` and restart both servers.
2. **Provider** saves your own API key, as in **Settings**. The step names the provider that search uses (`EMBEDDING_PROVIDER`). Search works only once that provider has a usable key, so save one for it even if you chat with another provider.
3. **Model** chooses your default chat model and loadout, as in **Settings**. Its Test checks that the model answers and can call a tool.
4. **Server** checks that the database answers and has pgvector, and reminds you to keep a copy of `KEY_ENCRYPTION_KEY`. It also shows whether users may add a custom provider and whether connectors are on (see [docs/connectors.md](connectors.md)).

**Finish** is enabled when every required item is OK: the database, the key encryption key, login, the search key, and a default chat model. The allow-list is a warning only. After Finish, setup is closed for good. `/setup` then says that setup is not open, and the backend prints no more tokens.

The key and models you save in the wizard are your own, like everything in **Settings**. Every other user saves their own key and chooses their own models in **Settings**.

An install that already had users when it was upgraded to this version counts as set up, so it prints no token.

## What each setting is set by

The wizard writes no instance-wide option. The environment always decides, so there is no precedence to remember.

| Option | Set by | The wizard |
|---|---|---|
| Auth mode and its settings | `AUTH_MODE`, `OIDC_*`, `FIREBASE_*`, `SESSION_SECRET`, `APP_BASE_URL` | shows them and names the variables |
| Allow-list | `AUTH_ALLOWED_EMAILS` | shows it, and warns when it is not set |
| Database, key encryption key | `DATABASE_URL`, `KEY_ENCRYPTION_KEY` (from the setup script) | checks them |
| Provider presets, custom provider | `PROVIDERS_CONFIG_PATH`, `ALLOW_CUSTOM_PROVIDER` | shows them |
| Embedding model | `EMBEDDING_PROVIDER`, `EMBEDDING_MODEL`, `EMBEDDING_DIMENSIONS` | names the provider that needs a key |
| Connectors ([docs/connectors.md](connectors.md)) | `MCP_ENABLED`, `MCP_USER_CONNECTORS`, `MCP_CONNECTORS_PATH`, and the token variables `connectors.yaml` names | shows them |
| The wizard itself | `SETUP_WIZARD` | — |
| Each user's keys and models | the user, in **Settings** or the wizard | saves them through the settings APIs |

## Skip the wizard

Set `SETUP_WIZARD=false` in `.env` to install without the wizard, for example from a script or in CI. The backend then prints no token, and `/setup` says that setup is not open. Everything the wizard shows is already set by the environment, so nothing is lost. Each user saves their own key and chooses their own models in **Settings**.

When the providers file (`PROVIDERS_CONFIG_PATH`) offers a provider whose preset needs no key (`key_required: false`), such as a local Ollama, no user has to save a key. They can choose its models in **Settings** right away. A script that needs a default model for a user sets it with `PUT /api/settings/models`, like any client.

Demo mode never opens setup. Setting `SETUP_WIZARD=true` in demo mode stops the backend from starting.

## The doctor

The doctor checks an install from the command line, with no login and no running backend. It reports the settings, the configuration files, the database, the migrations, whether setup is open, the login provider, and whether each provider and connector can be reached. It never prints a secret or the setup token.

Run it with the same `-f` files that the install uses:

```sh
docker compose -f docker-compose.yml -f docker-compose.pocket-id.yml run --rm --entrypoint python backend -m app.doctor; echo $?
```

When Postgres is the suspect, add `--no-deps`, so compose does not wait for Postgres to be healthy:

```sh
docker compose -f docker-compose.yml -f docker-compose.pocket-id.yml run --rm --no-deps --entrypoint python backend -m app.doctor; echo $?
```

With `COMPOSE_FILE` in `.env` (step 2), drop the `-f` files:

```sh
docker compose run --rm --entrypoint python backend -m app.doctor
```

`--entrypoint python` skips the migrations that the backend runs when it starts, so the doctor also runs when the backend cannot start. Each line reads `ok`, `info`, `warning`, `failed`, or `skipped`, followed by the item and a message. The exit status is 0 when nothing failed and 1 otherwise. Add `--json` for the same report as JSON.

The frontend checks its own settings when it starts. Read `docker compose logs frontend` for those.

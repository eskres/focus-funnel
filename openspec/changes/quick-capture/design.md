## Goals / Non-Goals

**Goals:**

- A capture is a `/push` in every way the user's key, the model, and the stored proposal can tell: same tools, same rules, same cost. No second path to proposals.
- No thought is stored before the user confirms a card, and a refused capture stores nothing at all. A capture's conversation, message, and pending proposal are stored as for any `/push`, which the confirm-to-save rule already allows.
- The share target works logged in and logged out, for long texts: at least 10,000 characters in any script (decision 12). The shared text reaches the app's own server once, in the `/share` request line, and is never stored or logged there; no later request carries it, and it is never in the login address.
- Text kept in the browser for a capture never lands in another user's box.
- No user data in any browser cache.

**Non-Goals:**

- Offline use, or queueing a capture made offline. The service worker answers no request (decision 13).
- A share target for files or images. The manifest takes `title`, `text`, and `url` only.
- iOS share sheet support. Safari does not offer web share targets; the Capture page works there as a page.
- A Stop button on the Capture page. Dismiss stops and deletes a running capture (decision 8); the chat's Stop works when the capture is opened as a conversation. A capture stopped either way is not shown as failed (decision 7).
- Choosing a model, effort, or connector on the Capture page. A capture uses the default; changing it is done in Settings.
- Making the rest of the app fit a phone. Only the Capture page and `/share` are laid out for one.
- Push notifications when cards are ready.
- A CSRF token or an `Origin` check on the API as a whole (decision 15 explains why capture needs neither).
- Showing the model's reply text, the usage meter, or the usage warning notice on the Capture page. A capture leaves the warning for the next chat answer (decision 5).

## Decisions

### 1. The Capture page is `/capture`, outside the app layout

The box lives on its own page, `/capture`, with a layout of its own (`app/capture/layout.tsx`): a slim header with the app's name linking to `/app`, the `DemoBar` in demo mode, and a single column at most `max-w-xl` wide with a 16 pixel gutter. The layout wraps the page in `DemoProvider` and `CategoriesProvider`, which the card and the sheet need, as `app/app/layout.tsx` does. The page mounts its own `ThoughtSheet`, as the Upcoming and Library pages do. It is reached from a sidebar link "Capture" beside "Upcoming" and "Library", and from the installed app's shortcut (decision 11). `/share` opens it too (decision 12).

**Alternatives:** a box in the sidebar (rejected: the sidebar is a fixed 256 pixel column that a phone cannot show beside anything, and its job is the conversation list); a box in the header (rejected: on every page, including settings, for an action most users take from the phone); on the Library page (rejected: the Library lists filed thoughts, and cards waiting to be confirmed are not filed); `/app/capture` inside the app layout (rejected: the sidebar leaves about 100 pixels on a phone; making the whole layout responsive is a separate piece of work).

### 2. A capture is a conversation of its own, run as a `/push` turn

Each capture makes one new conversation, stores one user message `/push <text>` in it, and runs one turn with the proposal tool forced, through the same code `POST /api/chat` uses for a first `/push` message. Everything the specs say about a `/push` then holds with no new code: the raw text is the text without the command, the similar-thought check and its refs (`details.similar` on the tool message), the mark parts, the date parts in the request's zone, one proposal per answer, the round limit, background running, the usage rows. The proposal, confirm, and origin are the existing ones, so a saved thought's origin is the capture's conversation. The sidebar does not list it (decision 3).

The stored message keeps the `/push` prefix, so a capture opened as a conversation reads as what it was, and `raw_text_for(..., push=True)` gives the user's text. The title is `title_from(text)`, without the prefix.

**Alternatives:**

- A proposal not tied to a conversation, from a dedicated endpoint that answers the parts (rejected: `proposals.conversation_id`, the proposal's position, its raw text, the confirm route, the origin, the refs of `thought-appending`, and the candidate round of the similar-thought check all need a conversation; a second path would copy the turn loop and drift from `/push`).
- One hidden inbox conversation per user (rejected: every capture would send all earlier captures to the model as context, cost grows with each one, and the full-context refusal would start to hit; the raw-text and held-proposal rules would mix captures).
- An ordinary conversation, listed in the sidebar (rejected: the story is "without opening a conversation", and a phone that shares a few links a day would fill the sidebar).

### 3. `conversations.capture_state` marks a capture and whether it waits

One nullable column on `conversations`: `capture_state` (`String(8)`), with a check constraint for `open` or `closed`, and a partial index `ix_conversations_open_captures` on `(user_id, created_at)` `WHERE capture_state = 'open'`.

The model declares the constraint as `CheckConstraint("capture_state IN ('open', 'closed')", name="capture_state")` in `Conversation.__table_args__`; the naming convention in `app/db.py` makes it `ck_conversations_capture_state`. Naming it `ck_conversations_capture_state` in the model would render as `ck_conversations_ck_conversations_capture_state` (`thought-status` decision 3). The migration adds the column and `op.f('ck_conversations_capture_state')` inside `op.batch_alter_table("conversations")`, as `setup_state` and `thought-status` do, so SQLite rebuilds the table. The index gives both `postgresql_where` and `sqlite_where`, so the SQLite migration test builds it too.

- `NULL`: an ordinary conversation. Every existing row.
- `open`: a capture listed on the Capture page.
- `closed`: a linked capture (below) whose every part is confirmed, or that was dismissed (decision 8). Kept as the origin of its thoughts, listed nowhere. Parts not confirmed stay unconfirmed in its conversation, as in any chat proposal.

A capture is *linked* while a thought points to it: a row in `thoughts` whose `proposal_id` is one of its proposals (the thought's origin), or a row in `thought_additions` whose `proposal_id` is one of them (an addition, undone or not). A confirmed mark does not link: it sets the part's `thought_id` to a thought whose origin is elsewhere, and records nothing there. A deleted thought takes its link with it; its addition rows go by cascade. Only a linked capture is ever `closed`, so every stored capture is reachable: an `open` one from the Capture page, a `closed` one from a thought's origin or additions list, and both are deleted with "Delete content". The test is one `EXISTS` over each of the two tables, by the capture's proposal ids, and runs only in a confirm that leaves no part unconfirmed, a dismiss, and a thought delete, never in the list.

Where it changes:

| Event | `capture_state` |
|---|---|
| `POST /api/captures` makes the conversation | `open` |
| Confirm leaves no part of the conversation's proposals without `thought_id`, and the capture is linked | `open` → `closed`, by a conditional update in the confirm's transaction (decision 7) |
| `DELETE /api/captures/{id}` on a linked capture | `open` → `closed` (decision 8) |
| `DELETE /api/thoughts/{id}` leaves a `closed` capture unlinked | `closed` → `open`, in the delete's transaction (below) |
| `POST /api/chat`, other than `/compact`, claims it to answer a message, whether or not a new message row is written | `NULL`, in the commit that clears `archived_at` (decision 9) |
| Archive, restore, rename, `/compact` | unchanged |

`GET /api/conversations` lists only rows with `capture_state IS NULL`. A confirmed mark has a `thought_id` (`thought-status` decision 7), so it counts as confirmed here, while the held proposal still leaves marks out. A capture whose turn wrote no proposal stays `open` until it is dismissed, and so does one whose confirmed parts are only marks: with every card confirmed it stays listed, its cards marked done, until the user dismisses it, which deletes it.

`delete_thought()` gains one step, in its transaction, for the route `DELETE /api/thoughts/{id}`: before the delete it reads the ids of the user's `closed` captures the thought links (the conversation of its `proposal_id`, and those of its `thought_additions` rows), and after the delete, before the commit, it runs `UPDATE conversations SET capture_state = 'open' WHERE id IN (:ids) AND user_id = :u AND capture_state = 'closed' AND NOT <linked>`. A capture that still has another saved thought stays `closed`. One that the delete left unlinked is listed on the Capture page again, with its saved card shown as deleted, and can be dismissed, which deletes it. A thought from an ordinary conversation reads no id and runs no update.

**Alternatives:** a `kind` column, with "waits" worked out from the parts' JSON on every list (rejected: the list would scan the JSON of every capture the user ever made, or cap the scan and lose old waiting ones); count any confirmed part, a mark included, as a link (rejected: a capture whose only confirmed card marked a task done would close with nothing pointing to it, and the user's text would stay stored where no page shows it); close a capture of only marks and delete it on confirm (rejected: the card's "Marked done" state would vanish under the user, and confirm would become a delete); leave a `closed` capture closed when its last thought is deleted (rejected: the same text stored where nothing reaches it, with only "Delete content", which deletes everything, to remove it); delete the capture with its last thought (rejected: a thought delete would silently delete the cards not yet confirmed, which the user may still want); `held_proposal_id` as "waits" (rejected: a proposal of only marks is never held, and a capture with no proposal has none); `archived_at` (rejected: archived conversations are listed under "Archived", and a message restores them); deleting the capture once every part is confirmed (rejected: the thought would lose its origin).

### 4. `POST /api/captures`

Body: `{"text": str, "time_zone": str | null}`, with `extra="forbid"`, so a `conversation_id`, `model`, or `provider_id` gets 422 naming the field. The steps, in order:

1. `text` is stripped. Empty gives 422 `validation_error` `text: must not be empty`; over `MAX_RAW_TEXT` (20,000) characters gives `text: must be at most 20000 characters`. Nothing is read or stored yet.
2. `get_default_model()`. None gives `model_not_set()`.
3. `cap_state()`. Reached gives `spend_cap_reached()`.
4. Make the conversation with `new_conversation(user, text, default)`, `capture_state="open"`, `turn_started_at=now()` (the claim, as for a first chat message), and the user message `/push <text>` at position 0. Commit, so the claim is visible to a delete (`stop-and-spend-cap` decision 13).
5. Start the turn through `start_turn()` (decision 5), with the request's zone. When `check_room()` in it finds that the text does not fit the default model's context, `create_capture()` catches the `context_full` error and raises one with the same status and code and the message "This text is too long for <model>. Shorten it, or set a default model with a larger context in Settings.", since the chat's text points to `/compact` and a new conversation, which the Capture page does not have. The context-management delta states this refusal beside the chat's (decision 18).
6. Answer `202` with `{"capture": <item>}`, the item of decision 6 with `running: true`.

Any error in step 5 rolls back, deletes the conversation by id (its message goes with it by cascade), commits, and is raised as it is, with no `X-Conversation-Id`. So a refused capture stores nothing, and the page keeps the text in the box. Steps 1 to 3 store nothing to begin with.

The answer does not stream. The turn runs in the registry with no subscriber, and the page follows it by loading the list (decision 6). A phone often drops a long request when the user switches apps; this way nothing depends on that request.

On the page, "Make cards" is off from the press until the answer comes, since step 5 can take seconds on a phone and a second press would start a second paid turn. A refusal turns it on again with the text kept. When the request fails with no answer at all (a network error), the server may have started the capture anyway, so the page keeps the text and loads the list once; a capture that did start then shows under the box, and the user can dismiss it or leave it. A 401 `unauthenticated` (`UnauthenticatedError`) stores the box text (decision 12) and sends the user to log in. A 401 `demo_session_expired` stores nothing and does not redirect: `DemoProvider` shows its ended screen (decision 16). "Make cards" is also off until `getMe()` has answered (decision 12).

The page shows a refusal with `ChatError` and `showRetry={false}` (decision 7), so a key, model, or cap refusal has the chat's alert and link. For `context_full` it passes `title="This text is too long"`, since the class's own title, "This conversation is full", names a conversation the page never shows.

**Alternatives:** keep "Make cards" on during the request and dedupe on the server by text and time (rejected: two equal captures a minute apart can be meant; turning the button off is the usual form rule); a `capture: true` flag on `POST /api/chat` (rejected: the chat's request takes a model choice, `/compact`, and commands, and keeps a refused message, which are all wrong for a capture; one more mode in that route would be harder to read than a second short route); answer the SSE stream as `POST /api/chat` does (rejected: the page would need a second, live path beside the list, and the phone drops it anyway); the chat's order, storing the message before the checks (rejected: a capture refused at the cap or for a missing key would leave a capture with no answer, which the user never asked to keep; the box already keeps the text); keep a refused capture in the list with its error (rejected: same reason, and "Try again" on it would be one more step than pressing "Make cards" again). For a text too long for the model: show the chat's `context_full` text (rejected: it names `/compact` and a new conversation, neither of which the page offers); a message argument on `check_room()` (rejected: one caller needs it; catching the error in the one route that does keeps the chat's code as it is). For its title: show `context_full` in a plain `Alert` (rejected: a second way to render refusals beside `ChatError`, for one code; an optional `title` is one prop).

### 5. One turn start for the chat and for captures

The part of `chat()` from building the context to `turn.open()` and handing the turn to the registry moves into `start_turn(session, user, conversation, message, *, command, zone, config, settings, http_client)` in `app/routers/chat.py`. `chat()` calls it for every message, as today. `create_capture()` calls it with `command="push"`. It forces `PROPOSE_TOOL` for `push` and `SEARCH_TOOL` for `pull`, as `FORCED_TOOLS` does now, passes the zone to `build_context()` and the turn, and passes `info` to `Turn` (`stop-and-spend-cap` decision 4). The capture's conversation is new, so no held proposal, seen thoughts, connector, or action expiry applies; the shared code reads them as for any new conversation and finds none.

`start_turn()` takes `warn: bool = True` and passes it to `Turn`. `create_capture()` passes `warn=False`, and `Turn._note_usage` then records the round but does not call `usage_warning()`. A capture always runs with no viewer, so a notice it sent would mark the month warned with no one to see it, against usage-tracking "A warning threshold". With the flag, the month stays unwarned, and the next chat answer that records usage sends the notice. The Settings usage section shows the threshold passed in the meantime, as it reads the month's totals.

**Alternatives:** copy the steps into the capture route (rejected: two copies of the order that `background-turns` and `stop-and-spend-cap` each change, which would drift). For the warning: keep it and modify usage-tracking so a threshold crossed in a capture shows only in Settings (rejected: the notice exists to be seen in the chat, and skipping one call keeps it); show the notice on the Capture page (rejected: the page would need the turn's events, which it does not read, decision 6).

### 6. `GET /api/captures`, and how the page follows a running capture

`GET /api/captures` answers `{"items": [...], "more": bool}`: the user's captures with `capture_state = 'open'`, newest first (`created_at DESC, id DESC`), at most 50, with `more` when a 51st exists. The select is `owned_by(Conversation, user)` on the partial index. With `ids` (repeated, `?ids=<id>&ids=<id>`, at most 50, more answers 422 `validation_error`), it answers only those of the asked ids that are the user's `open` captures, in the same shape and order, with `more` false; another user's id, an unknown one, a `closed` capture, and an ordinary conversation are left out with no error. Each item:

```
{"id": <conversation id>, "created_at": ..., "text": "<the text, without /push>",
 "running": bool, "proposal": <ProposalOut> | null, "error_code": str | null}
```

- `text` is the first user message through `parse_message()`, so the prefix is dropped.
- `running` is true when the registry holds a turn for the conversation, or when `turn_started_at` is set and newer than `TURN_CLAIM_TIMEOUT`. The second covers the seconds between step 4 and the registry hand-off of step 5, while `model_info()` may fetch the model list: the capture holds the claim but is not in the registry yet, the same claim `stop-and-spend-cap` decision 13 relies on. Without it, a load from another tab would read `running: false` and no proposal, and offer "Try again" on a capture that is starting. After a restart, `background-turns`' start-up sweep has already stored `answer_interrupted` and cleared the claim before the server serves, so the capture reads `running: false` with that `error_code`, and the page shows "The server restarted before the cards were made." with "Try again". Only a second process sharing the database leaves a claim that reads as running until `TURN_CLAIM_TIMEOUT`.
- `proposal` is the conversation's latest proposal, in the same shape as in the conversation's messages answer, built by `proposal_payload()` with the saved-title map and `thought-appending`'s `target` and `similar`, so the card has one shape everywhere.
- `error_code` is the last assistant message's `error_code` when no turn is running, else null. A stopped turn's `answer_stopped` is passed as it is; the page reads it as no error (decision 7).

It runs a fixed number of queries whatever the number of items: the conversations, then their messages, their proposals, and the saved titles, each with `IN`. It makes no provider call.

The page loads the full list on open and when the tab becomes visible again. While any shown capture is `running` and the tab is visible, it loads every 3 seconds, one request at a time, only the shown running captures, with `ids`. Each item carries its full text (up to 20,000 characters) and its proposal, so a poll of the full list could move about 1 MB every 3 seconds on a phone with many captures waiting; the filtered load moves only what can still change. A hidden tab makes no load; the load on becoming visible picks up from there. The full load adds new captures and updates the shown ones; the filtered load updates the ones it asked about.

The page notes, for each item, when it added it. A shown item that a load covers (every shown item for the full load, the asked ids for the filtered one) and leaves out is no longer listed, when that load started after the item was added: every card confirmed, dismissed or tried again in another tab, carried on as a conversation, or refused by the server after step 4 and deleted. An unlisted item with a proposal stays shown until the user leaves the page, so a card just confirmed keeps its "Saved" link in view, but it shows as not running, no longer drives the 3-second load, and loses "Dismiss" and "Try again" (decisions 7 and 8). An unlisted item with no proposal is removed from the page: it has no link worth keeping, and in most of those cases its conversation is gone, so "No cards were made." would be false and its "Open" link would answer 404. A load that started before the `POST` answered never changes the new item. This matters for a capture whose only card the user confirms while its turn still runs: `Turn.events()` stores the proposal in the tool round, and the model's reply round runs after it, so the card shows while `running` is still true; the confirm closes the capture, the next load leaves it out, and the page stops showing "making cards" and stops loading.

Until a full load has succeeded, the list shows "Loading captures…". "Nothing waits." shows only after a load that succeeded, when no item is shown. A load that fails keeps the shown items as they are:

- 429 `rate_limited` shows no alert, does not redirect, and waits `Retry-After` seconds, or 30 seconds without the header, before the next load. `listCaptures()` reads the header onto the error as `retryAfterSeconds`.
- 401 `unauthenticated` (`UnauthenticatedError`) stores the box text (decision 12) and sends the user to log in, as for the `POST`. 401 `demo_session_expired` stores nothing, does not redirect, and makes no further load: `DemoProvider` shows its ended screen (decision 16).
- Any other failure (a network drop, 5xx, `backend_unreachable`) shows the error's message above the list, and the 3-second load goes on while a shown capture runs. The next good load removes the message.

A full load that fails is tried again, whether or not a capture runs: after the 429's wait, or 10 seconds after any other failure. Without that, a failed load on open, with nothing shown yet, would never be tried again until the tab is hidden and shown, and a 429 would leave an empty page with no message; in demo mode, where all visitors share one limit, that is likely. A retry that comes due while the tab is hidden waits for the load on becoming visible.

**Alternatives:** poll the full list (rejected: the size above, every 3 seconds, for items that cannot change); a `?running=1` filter (rejected: a capture that has just finished is no longer running, so the load that should bring its cards would leave it out); keep an unlisted item's last `running: true` (rejected: the spinner would stay and the page would load until the user leaves it, eating into the shared demo rate limit); follow each running capture through `GET /api/chat/{id}/stream` (rejected: one open stream per running capture, a second event path in the page, and the list still has to be loaded on return); poll every second (rejected: in demo mode every request counts against a per-minute limit that all visitors share, and a capture takes seconds; 3 seconds is 20 requests a minute at most, and only while a capture runs in a visible tab); show a 429 as an alert (rejected: in demo mode it is the shared limit, not the user's doing, and the next load usually works); retry a failed full load only while a capture runs (rejected: a failed load on open would leave the page empty for good); keep an unlisted item with no proposal, as one with cards is kept (rejected: its conversation is usually gone, above); branch on the 401 status rather than on `UnauthenticatedError` (rejected: `demo_session_expired` is a 401 too, and the rest of the app branches on the class); show every capture ever made, with a filter (rejected: nothing on the page is for done captures; their thoughts are in the Library).

### 7. Cards on the page, and closing a capture on confirm

Each item with a proposal renders `ProposalGroup` with `conversationId` set to the capture's id, so merge, confirm, the addition card, the "Similar" hint, the date fields and choices, and the mark card all work as in the chat. Confirm goes through the existing route. Its owner check, its lock, and its repeat-confirm answer are the chat's.

The confirm route gains one step in its transaction, before its commit: when none of the conversation's proposals has a part without `thought_id`, it runs `UPDATE conversations SET capture_state = 'closed' WHERE id = :id AND capture_state = 'open' AND <linked>`, with the link test of decision 3. The thought or addition row the confirm just wrote is in the same transaction, so a capture whose last confirmed card saved a thought closes, and one whose confirmed cards only marked tasks done stays `open`. It does not assign the attribute on the `Conversation` that `get_conversation()` loaded earlier: the route locks only the proposal row, not the conversation, so a chat message in another tab may have set `capture_state` to `NULL` since that load (decision 9), and an assignment would write `closed` over it and hide a conversation the user writes in from both the sidebar and the Capture page. The conditional statement leaves a `NULL` as it is. The addition confirm (`mode: "add"`) and the mark confirm run through the same route, so the same statement runs after them; an addition links, a mark does not.

`error_code` `answer_stopped` is not an error on the page, as `stop-and-spend-cap` says a stopped answer "is not shown as a failure". A capture can end stopped: the chat's Stop on a capture opened from a card's origin while its turn runs, or a dismiss that stops the turn and then answers 409 because the turn outlasted the bound. The page reads it as no error code. With a proposal, it shows the cards with no reason under them. With none, it shows "No cards were made." with "Open" and "Dismiss" and no "Try again", as below, so the stopped reply is never deleted unasked.

The page shows the reason for any other `error_code` with `ChatError`, so a key, model, or cap error shows the same alert and link as in the chat. The error is built by a new `storedError(code)` in `lib/api.ts`, which gives the code's error class a message per code: `provider_unreachable` "The provider could not be reached. Try again in a moment.", `provider_rate_limited` "The provider is getting too many requests. Try again in a moment.", `answer_interrupted` "The server restarted before the cards were made.", `output_limit_reached` "The model ran out of room before it made the cards.", `tool_loop_limit` "The model did not finish making the cards.", `spend_cap_reached` "Monthly spend cap reached.", and for any other code "The cards could not be made." The chat's `fromStored()` keeps its own text, which points to sending the message again, an action the Capture page does not have. A capture with no proposal and no error code says "No cards were made." with an "Open" link to `/app/<id>`. An error after the cards were shown (a proposal and an `error_code`, such as the cap reached after round 1) shows under the cards, and the cards stay.

`ChatError` gains `showRetry` (default `true`) and `title` (optional; it replaces the title of the error's class). The Capture page passes `showRetry={false}`, so the error shows no button of its own, and the item has one "Try again"; for a `ContextFullError` it passes `title="This text is too long"` (decision 4). "Try again" shows only on an item with no proposal and an `error_code` other than `answer_stopped` that the latest load lists, `open` and not running. It puts the text in the box (after a new line when the box already holds text, so nothing typed is lost), then dismisses it through the capture delete of decision 8, with no dialog: nothing of it was confirmed, and the turn failed. If the delete fails, the text stays in the box and the reason shows. An item with no proposal and no `error_code` holds the model's reply, which its "Open" link points to; it offers "Open" and "Dismiss" (with its dialog) only, so nothing deletes that reply unasked.

**Alternatives:** a capture-only card (rejected: the card already handles every kind of part, and a second one would miss the next kind a change adds); close the capture when the page next loads the list (rejected: the list query would have to read every part again, which decision 3 avoids). For the reason: move `fromStored()`'s text into a shared helper and use it on both pages (rejected: it never names the failure, and "Send the message again" points to the chat); show the generic text and reword the scenario (rejected: the user cannot tell a provider outage from a bad key, and a per-code text costs one map). For a stopped capture: show `answer_stopped` as any code, through `storedError()` (rejected: "The cards could not be made." and "Try again" for an answer the user stopped, and "Try again" deletes the partial reply); map it to `null` in `GET /api/captures` (rejected: the API would hide what is stored, and the chat reads the same code as stopped already). For the button: keep `ChatError`'s "Try again" and wire it to the item's (rejected: it shows for three codes only, so the item would still need its own for the rest, two paths for one action); "Try again" also on an item with no cards and no error (rejected: it would delete, with no dialog, the reply the item's "Open" link points to). For closing: assign `capture_state` on the loaded conversation (rejected: it can overwrite a concurrent `NULL`, above); lock the conversation row in the confirm (rejected: a second lock order beside the proposal row's, for what one conditional statement does).

### 8. Dismiss deletes or closes the capture, through a capture route

"Dismiss" opens `DeleteDialog` with the heading "Dismiss this capture?", the confirm button "Dismiss", and a text that says what will happen. `DeleteDialog` gains `confirmLabel` (default "Delete"), since a dismiss that closes keeps the conversation. The text depends on the item as the page has it: when no part has a `thought_id` with no `mark` and is not `deleted`, so nothing links to the capture (decision 3), it is "The text and its cards are deleted."; otherwise it is "Cards you have not confirmed are not saved as thoughts. They stay in the capture's conversation, which the saved thoughts link to." On confirm it calls `dismissCapture(id)`, which sends `DELETE /api/captures/{id}`. A 409 `conversation_busy` shows "This capture is still making cards. Try again in a moment." in the dialog, in place of `conversation_delete_busy()`'s text, which names a conversation the page never shows. The route, in order:

1. Reads the conversation with `owned_by` and `capture_state = 'open'`. Any other row (another user's, a `closed` capture, an ordinary conversation) or none answers 404 `not_found` at once, with the same body as an unknown id: nothing is stopped and nothing is claimed.
2. Calls `stop_turns(user.id, id)`, as `DELETE /api/conversations/{id}` does (`stop-and-spend-cap` decision 13). A running capture's turn ends through its stopped store, and no model call follows.
3. Claims it with `claim_turn(..., busy=conversation_delete_busy)`, which commits on its own. A turn that outlasts the bound answers 409 `conversation_busy` with that text, and so does a capture whose `POST` still holds the claim before `turn.open()`: it is not in the registry yet, so `stop_turns()` found nothing. The dialog shows the page's own text for it (above), and nothing is deleted. The stop may already have ended the turn as `answer_stopped`, so the capture stays listed as stopped (decision 7). The claim keeps a chat message from another tab out until the end.
4. In one transaction, locks the conversation's proposal rows with `SELECT ... FOR UPDATE` and reads whether the capture is linked (decision 3). A confirm locks its proposal row, so a confirm in flight commits first and one that comes later waits.
5. Not linked (nothing confirmed, only marks confirmed, or every saved thought since deleted): `DELETE FROM conversations WHERE id = :id AND user_id = :u AND capture_state = 'open'`. Linked: `UPDATE conversations SET capture_state = 'closed', turn_started_at = NULL WHERE id = :id AND user_id = :u AND capture_state = 'open'`, so every saved thought keeps its origin, and the parts not confirmed stay unconfirmed in the conversation, as in any chat proposal. When the statement touches no row, the route rolls back, releases the claim, and answers 404 `not_found`. Otherwise it commits and answers 204.

The order matters. `claim_turn()` updates by id alone and commits, so a claim taken before the owner check would write `turn_started_at` on another user's row (their own send in that moment gets 409), and for another user's running capture it would answer 409 `conversation_busy`, which tells them the id exists. A `stop_turns()` before the `capture_state` check would stop a chat answer running in a conversation the user carried on in another tab, against `stop-and-spend-cap`'s rule that a turn stops only when its owner asks or its conversation is deleted. Step 5's statements are guarded, rather than trusting step 1's read, because the confirm route never looks at the claim: a confirm in another tab can close the capture after step 1. Postgres re-checks the `WHERE` after the row lock, so such a capture is left as it is.

"Dismiss" shows on an item that the latest load lists, running or not. An item the page keeps but no load lists has none (decision 6). A 404 from the route removes the item's "Dismiss" and "Try again" and shows the fixed text "This capture no longer waits." in place of the route's "Not found."; text that "Try again" already put in the box stays there. So a capture whose every card was confirmed, or one carried on as a conversation in another tab, is never deleted or changed from the Capture page.

**Alternatives:** call the generic `DELETE /api/conversations/{id}` (rejected: it never looks at `capture_state`, so a stale item could delete a closed capture and strip the origin from every saved thought, or delete an ordinary chat the user carried on in another tab, with no dialog on "Try again"); stop and claim first, then check, as `DELETE /api/conversations/{id}` does (rejected: see above); check `capture_state` only by a read before the delete (rejected: a confirm can close the capture in between); only hide the buttons on unlisted items (rejected: a load in flight can still be older than the other tab's change; the route has to check too); answer 409 for a closed capture (rejected: to this page it no longer exists as a capture, and 404 keeps one answer for every row it may not change); a hidden "dismissed" flag that keeps a capture with nothing confirmed (rejected: the user's text would stay stored where no page shows it and no button deletes it); always delete, so thoughts saved from it lose their origin (rejected: the card has no way to drop one part, so a user who saves two cards of three and does not want the third can only clear the capture by dismissing it; that common case would strip the origin from every saved card, and closing needs no state per part, since `closed` already means "listed nowhere"); show the route's "Not found." (rejected: it does not tell the user that the capture was finished or carried on); delete or close by "a part has a `thought_id`" (rejected: a confirmed mark links nothing, so a closed capture of only marks would be stored where nothing reaches it, decision 3); one dialog text for both outcomes, "Cards you have not confirmed are dropped." (rejected: a closed capture keeps them in its conversation, where they can still be confirmed, so a user dismissing text they regret would be told it is gone when it is not); a new `DismissDialog` (rejected: a copy of `DeleteDialog`'s busy state and error line for one label); show `conversation_delete_busy()`'s text (rejected: "Try deleting again" and "this conversation" name things the page does not show).

### 9. A message sent in a capture makes it an ordinary conversation

A capture can be opened in the chat from a thought's origin, or from "Open" on a capture with no cards. `POST /api/chat` with that conversation id sets `capture_state` to `NULL` wherever `chat()` sets `archived_at = None`: for every message other than `/compact` that claims the conversation, in the commit that follows, whether or not a new message row is written. `_store_user_message()` writes no row when the text equals the last unanswered user message, which is how the chat retries a failed answer; tying the change to the stored row would leave a capture whose turn failed, opened with "Open" and resent from the chat as the same `/push <text>`, on the Capture page. From then on the sidebar lists it, the Capture page does not, and the origin shows its title. `/compact` claims nothing here and leaves it a capture, and a message refused as busy (409 `conversation_busy`) changes nothing; the conversations delta says so in its requirement.

**Alternatives:** clear it only when a message row is stored (rejected: a resend stores none, above); refuse a message in a capture (rejected: the user opened it to carry on; there is no reason to stop them); keep it hidden after a message (rejected: a conversation the user writes in, but can only reach through a thought, would be lost to them).

### 10. A capture's thought shows its origin as any thought does

A thought saved from a capture has the capture's conversation as its origin. The sheet shows it as any origin: the conversation's title, which is `title_from(text)`, the start of the captured text, with the date of the proposal, linked to `/app/<id>?proposal=<pid>`. Opening it opens the capture's conversation at the card. `thought-origin`'s requirements hold as they are, so neither the API, the sheet, nor the spec changes. After a message in that conversation (decision 9) the origin is that conversation, with whatever title the user gives it.

`thought-appending`'s additions list keeps the same rule: an addition made from a capture is listed with the capture conversation's title, as the conversation has it now, linked to its card. Origin and additions then read the same way.

**Alternatives:** a `capture: bool` on the origin and on each addition, shown as "Quick capture" in place of the title (rejected: an API field, a `thought-origin` change that would contradict "The detail view shows the origin", a second state in the sheet, and the same for the additions list; the captured text tells the user more than a fixed label, and the link opens the capture either way); a label in the origin and the title in the additions (rejected: the same capture would read two ways in one sheet).

### 11. The manifest is `app/manifest.ts`

Next.js serves `app/manifest.ts` at `/manifest.webmanifest` as `application/manifest+json`, and links it from every page. It holds:

```
id: "/app", name: "Focus Funnel", short_name: "Focus Funnel",
description: "File away your thoughts and find them again.",
start_url: "/app", scope: "/", display: "standalone",
background_color: "#ffffff", theme_color: "#ffffff",
icons: [/icons/icon-192.png 192x192, /icons/icon-512.png 512x512,
        /icons/icon-maskable-512.png 512x512 purpose "maskable"],
shortcuts: [{name: "Quick capture", url: "/capture", icons: [192]}],
share_target: {action: "/share", method: "GET",
               params: {title: "title", text: "text", url: "url"}}
```

The shortcut is worth its scenario and its manual step because it is the one way into the Capture page on a phone that does not start from a share: the installed app opens `/app`, whose layout leaves about 100 pixels beside the sidebar on a phone (decision 1), so the sidebar link is hard to reach there. It reuses the 192 pixel icon, so it adds no file.

The icons are PNGs in `public/icons/`, made once from `public/icons/icon.svg` with a converter run outside the repository (for example `rsvg-convert -w 192 -h 192`), and committed with the SVG; the maskable one keeps the mark inside the middle 80%. Nothing in the build or the repository makes them.

**Alternatives:** a `scripts/make-icons.mjs` with `sharp` (rejected: `sharp` is only an optional dependency of `next`, so `npm ci --omit=optional` or an unsupported platform leaves it out, and adding it to `devDependencies` is a dependency for three files that change almost never); a static `public/manifest.json` (rejected: `app/manifest.ts` is typed, including `share_target`, and Next links it); `start_url: "/capture"` (rejected: the installed app is the whole app; the shortcut and the share target reach the Capture page); no shortcut (rejected: on a phone the only other ways in would be a share or the cramped sidebar).

### 12. The share target is a `GET` to `/share`, which hands the text over in browser storage

`/share` is a small client page (`app/share/page.tsx`, outside both layouts). In the browser, not through `searchParams`, so the server never renders the text, it reads `title`, `text`, and `url` from `window.location.search`, then at once calls `history.replaceState(null, "", "/share")`, so the values leave the address before anything else runs. It builds the box text with `sharedText()` in `lib/captures.ts`: each non-empty value, trimmed, on its own line. It goes through `title`, `text`, and `url` in that order, and leaves a value out when it equals a value already kept, or when another value contains it and is longer. So of two equal values the first is kept: Android apps often share the same string as subject and text, or as text and link. When that text is not empty, it writes `{text, at}` to `localStorage` under `ff:shared-capture`, inside `try`/`catch`. Then it calls `location.replace("/capture")` in every case. A share with no values, or only empty or whitespace ones, writes nothing, so it never replaces text that a 401 stored earlier, and the box opens empty. When storage throws, the box opens empty too: a browser that blocks site storage also blocks this site's cookies, so the login and the Capture page would not work there anyway.

The Capture page calls `getMe()` on mount for the user's id. "Make cards" stays off until it answers, so every entry a 401 stores carries a `user_id`; an entry without one would read as a logged-out share and fill the box of whoever logs in next. When `getMe()` fails, the page shows the error's message with a "Reload" button and keeps "Make cards" off; a 401 `unauthenticated` from it sends the user to log in and leaves any kept entry where it is, to be read after the login, and a 401 `demo_session_expired` leaves the page to `DemoProvider`'s ended screen. Once it answers, the page reads the key once, puts the text in the box when it is younger than 30 minutes and its `user_id` is missing or equal to the current id, and removes the key in every case. The page then makes no cards until the user presses "Make cards".

A logged-out user: `/share` needs no login (decision 14), so it stores the text and goes to `/capture`; the proxy sends that to the login with `returnTo=/capture`, and the login comes back there in every mode. The text is never in the login address or in the sealed login cookie.

The Capture page uses the same key when an API call answers 401 `unauthenticated` (`UnauthenticatedError`): it stores `{text, at, user_id}` with the id `getMe()` gave, then sends the user to log in, so the text comes back to that user. A 401 `demo_session_expired` (`DemoSessionExpiredError`) stores nothing and calls no `redirectToLogin()`: demo mode has no login, the ended session's user is gone, and `DemoProvider` already swaps the page for `DemoEnded`. A different user who logs in on that browser within 30 minutes finds an entry with another `user_id`, which the page drops unread. A logged-out share has no `user_id`, so it goes to whoever logs in next, which is the person holding the phone.

Logging out removes the key. `logOut()` in `lib/account.ts` becomes the one helper that does it: it removes `ff:shared-capture`, inside `try`/`catch`, then goes to `/auth/logout`. The four logout links become one `LogoutButton` (`components/logout-button.tsx`) that calls `logOut()`, and "Delete account" in `components/delete-data-settings.tsx` already calls it after the account is deleted. So `/auth/logout` appears in one place outside the route and its tests. "End demo" in `demo-bar.tsx` removes the key too before it ends the session. In demo mode a new session is a new user, so an entry stored for the old one is dropped by the `user_id` rule as well.

The shared text reaches the server once, in the `/share` request line, to the Next.js server and any reverse proxy in front of it. The proxy answers `/share` with `Cache-Control: no-store` and `Referrer-Policy: no-referrer` in every mode (decision 14), so the HTTP cache does not keep the address and no request that follows, the JS chunks, `/sw.js`, the move to `/capture`, or the login redirects, carries it as a `Referer`. `/share` is answered by the Next.js server, which logs no request line, and it never reaches the backend. The backend's access log does write a line for each `GET /api/captures?ids=...`, whose query carries only conversation ids, and `thought-library`'s record factory drops that query from the line. `docs/login.md`'s section "HTTPS on your network", which holds the `Caddyfile`, gains a note not to log query strings and that the reverse proxy must allow long request lines.

The request line counts toward Node's header limit, 16,384 bytes by default, and Node answers a longer one with 431 before the app runs, so the share would be lost with no message. 10,000 characters of `é` are about 60 KB once percent-encoded, and ASCII text with spaces, new lines, and punctuation, plus the session cookies, comes close to the limit too. The run stage of `frontend/Dockerfile` sets `ENV NODE_OPTIONS=--max-http-header-size=262144`, and the `dev` and `start` scripts in `package.json` set the same. That holds a share of at least 10,000 characters in any script (a character takes at most 12 bytes encoded) beside the cookies; a longer one is a risk the design accepts (Risks). Caddy's default allows request lines that long.

`history.replaceState` changes the address the page shows, but the browser has already recorded the `/share?...` visit in its history, and logout cannot remove that entry (Risks).

**Alternatives:**

- `POST` with `multipart/form-data` (rejected: a logged-out `POST` loses its body at the login redirect; the body would have to be read by a route or the service worker and kept somewhere first; and a `POST` that the page acts on needs CSRF care, decision 15).
- `GET` straight to `/capture?text=...` (rejected: logged out, the text goes into `returnTo` inside the sealed `ff_login` cookie, which is one cookie of about 4 KB, so a long shared text breaks the login; the text would also sit in the login address and in redirects).
- Make cards as soon as the page opens from a share (rejected: anyone can link to `/share?text=...`, so a link on another site would spend the user's key; and shared text often needs trimming first).
- `sessionStorage` (rejected: an installed app may open the share and the login in different browsing contexts; `localStorage` with an age, a single read, the user's id, and removal at logout is as private, since it stays in that browser).
- `Clear-Site-Data: "storage"` on the logout response (rejected: it also clears every other key of the origin and unregisters the service worker, and browsers differ on honouring it on a redirect; one `removeItem` in the link does what is needed).
- A `POST` share target that the service worker answers itself, so the text never leaves the phone (rejected: the worker would have to answer requests, which decision 13 rules out, and keep the body until the login is done).
- When storage throws, stay on `/share` with the text and a "Copy" button (rejected: with storage blocked, cookies are blocked too, so the login after it fails anyway).
- Keep Node's header limit and say shares stop at what fits in 16 KB (rejected: the goal is long texts, and a share over the limit is lost with no message).
- A `sharedText()` that leaves out any value contained in another, with no order (rejected: two equal values each contain the other, so both would go and the box would open empty or without the link).
- Remove the key in each logout link (rejected: `logOut()` after "Delete account" is a fifth path that would be missed, as the first plan missed it; one helper is one place).

### 13. The service worker caches nothing

`public/sw.js`, registered with scope `/` and `updateViaCache: "none"` by a small client component (`components/pwa/service-worker.tsx`) in the root layout, when `navigator.serviceWorker` exists. It has three listeners: `install` calls `skipWaiting()`, `activate` calls `clients.claim()`, and `fetch` does nothing. It never calls `respondWith()`, never opens `caches`, and imports nothing, so every request goes to the network exactly as without it, including the SSE streams and the login redirects.

The worker is there for the install, not for speed or offline use. Chrome on Android has not required a fetch handler for an install since version 108, but older versions did, and the share sheet only lists an installed app. A listener that never answers costs nothing in the browsers that skip such a listener, and gives the older ones what they ask for.

**Alternatives:** no service worker (rejected: older Android Chrome would not install the app, so it would not be in the share sheet); a caching worker, such as `next-pwa` or Workbox (rejected: a new dependency, and its default caches would keep pages and API answers that hold the user's thoughts, across a logout); an offline page (rejected: offline is a non-goal, and a cached page is still a cache to keep clean).

### 14. The proxy lets the install files and `/share` through

`proxy.ts` gets two lists, checked before the login check in every mode:

- Install files: `/manifest.webmanifest`, `/sw.js`, and paths under `/icons/`. In `oidc` and `firebase` mode they pass with no login. In `demo` mode they are rate-limited like every request, marked `no-store`, and never start a demo session (`demoRequest()` returns before `demoPage()`).
- `/share`: passes with no login in `oidc` and `firebase` mode, and is not sent to `/app` for a logged-in user, unlike `/`. In `demo` mode it goes through `demoPage()` as any page, so a visitor with no session gets one, which the Capture page needs next. In every mode, every response the proxy gives for `/share` carries `Cache-Control: no-store` and `Referrer-Policy: no-referrer` (decision 12): the page itself, the request limiter's 429, and `demoPage()`'s rewrites to `/demo/unavailable` (429 at the session limit, 502 or 503 when a session cannot start). On those the page's script never runs, so the text stays in the address, and the rewritten page's chunk requests would carry it as their `Referer` with the default policy.

The browser fetches the manifest with no cookies, so it must not need a login. `/capture` stays behind the login.

**Alternatives:** add the files to the matcher's exclusions (rejected: they would then skip the proxy in demo mode too, with no `no-store`, which the demo-mode spec asks of every response); make `/share` a public page like `/` (rejected: `/` sends a logged-in user to `/app`, which would drop the shared text).

### 15. Cross-site requests

Nothing that a link from another site can reach has an effect: `/share` and `/capture` are `GET` pages that store nothing on the server and call no model (decision 12). The one request that spends is `POST /api/captures`, which the page sends with `fetch` and a JSON body. A cross-site form cannot make it work: the session and demo cookies are `SameSite=Lax`, so a cross-site `POST` carries none and the proxy answers 401; and a form can only send a non-JSON content type, which the backend refuses with 422 before the handler runs. A cross-site `fetch` with JSON needs a CORS preflight that the app never allows. There is no `POST` share target (decision 12), so no CSRF token is needed.

**Alternatives:** a CSRF token on the capture form (rejected: there is no cross-site path left to defend, and a token needs storage and a refresh story); an `Origin` check in the proxy for every `POST` (rejected for this change: sound hardening for the whole API, but it touches every route, and capture needs nothing more than the above; listed in Non-Goals).

### 16. Demo mode

A demo visitor is a user like any other. The capture uses the visitor's held key, which the proxy sends with every API call, and the turn task keeps it (`background-turns` decision 6). Before the first capture, the page shows `DemoNoticeDialog` when `useDemo().noticeAccepted` is false, and sends the capture only after `acceptNotice()`, as the chat does before the first message. The visitor's captures are conversations, so they go when the session is deleted. When a call answers 401 `demo_session_expired`, the page stores nothing under `ff:shared-capture`, does not send the visitor to a login, and stops loading the list; `DemoProvider` shows `DemoEnded` (decisions 6 and 12).

`DEMO_RATE_LIMIT` (60 a minute by default) is shared by every visitor without `TRUSTED_PROXY=true` (`thought-library`'s context), and one Capture page with a running capture takes 20 of those a minute. So the page loads only while a capture runs in a visible tab, and backs off on a 429 without an alert (decision 6).

### 17. How it is checked

- Backend: pytest with the fake provider in `tests/chat_helpers.py`, for the endpoint, the list, the closing on confirm, the sidebar list, the origin, and a migration test.
- Frontend: vitest for `sharedText()`, the storage handoff, the Capture page, the proxy, the manifest object, and a static check of `sw.js`.
- Playwright: `@playwright/test` as a dev dependency, with `frontend/e2e/pwa.spec.ts` and `frontend/playwright.config.ts`, run with `npx playwright test` against a running app whose address is in `E2E_BASE_URL`. The app runs as the image runs it: built with `npm run build`, `public` and `.next/static` copied into `.next/standalone`, then `node .next/standalone/server.js` with the `NODE_OPTIONS` of decision 12, or the built frontend image. `next start` only warns on a standalone build and serves the files another way, so the checks of the manifest, `/sw.js`, and the icons would not cover how they are really served. It is not part of `npm test`. It checks what vitest cannot: the served manifest and its headers, the icons, the redirects of `/share` logged in and logged out, the service worker's scope, and that cache storage stays empty after use.
- A manual check on an Android phone, written out in the tasks: the share sheet itself cannot run in a container.

**Alternatives:** scratch Playwright scripts under `.context/`, as earlier changes did (rejected: these checks guard the install and the share flow for every later change, so they belong in the repository); Playwright inside `npm test` (rejected: it needs a running app and a browser download).

### 18. Spec deltas and archive order

- `conversations` "The sidebar lists conversations" is modified here. No open change modifies it (`mcp-connectors` adds a requirement; `stop-and-spend-cap` modifies "A conversation can be deleted with /delete").
- `context-management` "A message that cannot fit is refused" is modified here, starting from `mcp-connectors`' version of it, with one sentence for a capture whose text does not fit (decision 4) and a scenario. Without it, the requirement would say every such message gets the chat's advice and stays in the conversation, which a capture does not.

  **Alternatives:** leave the requirement as it is and state the capture's refusal only in `quick-capture` (rejected: two requirements would then disagree about the same `context_full`); modify it from the main spec's text (rejected: archiving after `mcp-connectors` would drop its tool definitions and connector advice).
- `thought-origin` is not changed: a capture's thought shows its origin under the existing requirements (decision 10).
- `usage-tracking` is not changed: a capture leaves the warning for the next chat answer, as "A warning threshold" asks (decision 5).
- The `quick-capture` spec refers to behaviour that `stop-and-spend-cap` (the cap), `thought-dates` (the zone), `thought-appending` (the similar-thought check and additions), and `thought-status` (marks) add, and the design relies on `background-turns`. The context-management delta starts from `mcp-connectors`' text. Archive this change after all six.

## Risks / Trade-offs

- [Depends on five planned changes, none built here] → The task groups say which one each needs. If `start_turn()`'s shape, the registry, `cap_state()`, or the zone helper differ when built, re-read decisions 4 to 6.
- [A usage warning that comes due during a capture waits for the next chat answer] → The usage section in Settings shows the threshold passed in the meantime, and the spend cap, which matters more, refuses with a visible reason.
- [Captures closed long ago stay stored as hidden conversations] → Only a linked capture is closed (decision 3), so each one is the origin of a saved thought or an addition and opens from that thought's sheet, and "Delete my content" removes them. A dismiss deletes a capture that nothing links to, a mark-only one included, and closes a linked one. Deleting the last thought that links a closed capture sets it `open` again, so it shows on the Capture page and can be dismissed.
- [A thought delete and a dismiss of the same capture at the same moment] → The dismiss can read the capture as linked just before the thought delete commits, and close it after the delete's reopening statement found it still `open`; the capture is then closed with nothing linking to it. Both need the same user acting in two tabs within milliseconds; "Delete content" still removes it.
- [The page polls while a capture runs] → At most 20 requests a minute, only while something runs in a visible tab, one at a time, with no provider call, backing off on a 429. Each load asks only for the running captures (decision 6), so it carries their text and cards, not up to 50 items.
- [Older Android Chrome may still not list the app in the share sheet] → Decision 13 gives older versions a fetch handler. The manual phone check records the browser version it ran on.
- [The shared text sits in `localStorage` until the Capture page reads it] → It stays in that browser only, is removed at the first read and at logout, an entry older than 30 minutes is dropped unread, and an entry stored for another user is dropped unread.
- [The shared text is in the `/share` request line, so a reverse proxy's access log would hold it] → The Next.js server logs no request line, `/share` never reaches the backend, and the proxy marks it `no-store` and `no-referrer`. `docs/login.md`'s section "HTTPS on your network" says not to log query strings; an operator who logs them anyway keeps shared text in that log.
- [The browser's history keeps the `/share` address with the shared text] → `replaceState` changes the address shown, but the visit is already recorded (Chrome records an installed app's navigations too), and logout cannot remove it; the user can clear it in the browser. This is the cost of a `GET` share target, which every alternative that works logged out accepts (decision 12). Task 7.2 records what Chrome shows.
- [A share longer than the raised limit, or a proxy in front with a lower one] → Node answers 431 before the app runs and the share is lost with no message. 256 KB holds 10,000 characters of any script with the cookies; a CDN or tunnel in front can have a lower URL limit of its own, which `docs/login.md` mentions.
- [A capture opened in the chat is not marked as one there] → The chat shows the `/push` message and the card, which is what it is. A message makes it ordinary (decision 9).

## Migration Plan

1. One Alembic revision adds `conversations.capture_state` (nullable), the check constraint, and the partial index. No backfill: every existing conversation is ordinary. It goes on top of the head when it is built; keep the single-head test passing.
2. Deploy the backend, then the frontend. An old frontend never makes captures, and its sidebar reads the same list endpoint, which only leaves captures out. A new frontend on an old backend gets 404 from `/api/captures`, which the page shows as an error.
3. Rollback: downgrade drops the index, the constraint, and the column. Captures made since become ordinary conversations and show in the sidebar. Nothing else changes.

## Context

See proposal.md for the problem. This change builds on `background-turns`, which is planned and not yet built on this branch: `backend/app/chat/running.py` does not exist yet. The Stop work is planned against its design and specs, which this change treats as in place:

- A turn runs as an `asyncio` task in a registry keyed by conversation id. A `RunningTurn` holds the owner's user id, an event log, and the task. Subscribers (the POST response and `GET /api/chat/{id}/stream`) replay the log and stop after the terminal `done` or `error` event.
- `run`'s shielded `finally` closes the model call, commits, releases the claim, and removes the entry.
- On `CancelledError` (shutdown), `Turn.events()` stores the round in flight as `failed` / `answer_interrupted` under `asyncio.shield`. The lifespan exit cancels every running turn and awaits them with a short bound.
- When the POST stream drops with no terminal event, the chat reloads the detail and follows the turn again, or shows the stored answer when the follow route answers `204`.
- `ConversationDetail.turn` tells a chat that loads a conversation to follow the running turn. A tab that already shows the conversation does not learn that another tab started a turn. Decision 5 of that change left Stop out and named `RunningTurn.task.cancel()` plus the cancel path as the follow-up.

It also builds on `mcp-connectors`, `thought-appending`, and `thought-status`, all stacked below and treated as in place:

- `mcp-connectors` moves the search and proposal code out of `_run_tool()` into `BuiltinTools` in `app/chat/tool_providers.py`. A provider's `call()` returns a `ToolOutcome` (text for the model, summary, event extras, `details`), and `_run_tool()` becomes a lookup of the owning provider plus the error handling. `ConnectorTools` calls MCP servers; a connector tool is named `<connector>__<tool>`, and built-in names have no `__`. An acts tool that needs approval writes a `pending` `tool_actions` row and emits an `action` event; an acts tool set to always allow, and a reads tool, call the remote server with no card. Every provider's `aclose()` runs in `Turn`'s cleanup. A provider's `call()` adds rows to the session and never commits. Approval runs outside a turn and is refused while one runs, so a turn only ever writes `pending` rows. When a turn starts, every `pending` or `failed` action of the conversation becomes `expired`, in the transaction that sets `turn_started_at`.
- `thought-appending` rewrites conversation-agent "The offer before an action may propose nothing": before archive or `/compact`, the model is asked whenever the user sent a message after the latest saved proposal. `thought-status` rewrites it again: a proposal whose only confirmed parts marked thoughts done does not count as saved. Decision 9 adds the cap exception to `thought-status`'s text.

The code as it stands on this branch:

- `Turn.events()` (`app/chat/turn.py`) stores each round as it ends. The text of the round in flight lives only in `RoundState`. A round with tool calls stores the assistant message with `tool_calls`, then one `tool` message per call. In `_run_tool`, the propose branch adds the proposal to the session, yields the `proposal` event, and only then commits it with the tool message.
- `read_round` reads usage as the provider's `stream_usage` capability says (`app/provider_config.py`): `final_chunk` (one report at the end), `incremental` (a report on every chunk, the last one counts), or `none`. Reported counts go into `RoundState.prompt_tokens` and `completion_tokens` as they arrive. It sends the `tool` start event as soon as a call's name arrives, before the call's arguments are complete and before the round is stored.
- `_note_usage` records each round with `record_usage` (`app/chat/usage.py`), which commits, then calls `usage_warning`, which reads `month_totals()`: the sums of `cost_usd` and tokens since the start of the month in UTC. When the warning is due, `usage_warning` sets `warning_notified_month`, commits, and returns the notice, which `_note_usage` yields. A stream with no usage chunk records nothing on a provider that reports usage.
- `_note_usage`, `_suggest_compact`, and `record_usage` each await `call.info()` (`app/chat/model_call.py`). On a miss in the five-minute per-user cache of `app/chat/model_info.py`, that fetches the provider's model list with the chat client and its timeout. `POST /api/chat` already resolves the same entry with `model_info()` for `check_room`, before the turn opens.
- The request's `AsyncSession` uses `expire_on_commit=False` (`app/db.py`), but `session.rollback()` still expires every instance in it, including `Turn.conversation`, which the route loaded with `get_conversation`. Reading any attribute of an expired instance, even its primary key, raises `MissingGreenlet` on an `AsyncSession`. No code in `turn.py` rolls back today.
- The terminal stores: `_store_failed` commits a `failed` answer before the error is raised; the `tool_loop_limit` end commits `error_code` on the last answer before it raises; the final `complete` or `cut` answer is committed by `_store`.
- The warning is saved in `user_settings` (`warning_unit`, `warning_amount`) through `PUT /api/settings/models`. That save checks every loadout model against its provider before it writes anything.
- `GET /api/usage` (`app/routers/usage.py`) reports the month in UTC and the warning state. The usage section is `components/usage-settings.tsx` with `id="usage"`; `USAGE_SETTINGS_HREF` is `/settings#usage`. "Delete usage history" is in `components/delete-data-settings.tsx`.
- `POST /api/chat` stores the user message, then sets the model (`_ensure_model`), then opens the call. For a new conversation it creates the conversation in that same commit. Refusals after the store carry `X-Conversation-Id`, and a resend of the same text is not stored twice: `_store_user_message` skips the store only when the last stored message is a user message with the same text.
- In `send()` in `components/chat/chat.tsx`, sending the same text as a `failed` or `cut` answer's prompt calls `retry()`, which clears that answer's text, tools, proposals, and sources and runs it again.
- `compact()` in `app/routers/chat.py` claims the turn and runs `_ensure_model`, but stores no user message and sets no `X-Conversation-Id`; its error path rolls back and releases the claim. In the frontend, `runCompact()` in `components/chat/chat.tsx` turns every error into `{step: "failed", message}`, which `CompactDialog` shows as plain text; it never goes through `ChatError`.
- `POST /api/conversations/{id}/proposal` (the offer before archive and `/compact`) returns a held proposal without a model call, or asks the model through `offer_proposal()`.
- Embedding calls go through `embed_texts()` (`app/thoughts/embeddings.py`) from search, store, update, additions, backfill, and `reembed.py`. They never raise to the caller; a failure leaves a thought without entries until a later call fills them in. `embed_texts` adds its `UsageEvent` to the session (`embeddings._record`) and leaves the commit to the caller. `search_thoughts()` commits by itself right after `embed_for_index` (`app/thoughts/search.py`), before it ranks, so in a turn the search's embedding row is committed while the tool call runs, not with the tool message. Store, update, additions, and `thought-appending`'s layer-1 check in `propose_thought` commit theirs with their own writes.
- `Message.status` is a free `String(16)`; no constraint lists its values. The frontend's `fromStored` treats any status other than `complete`, or any `error_code`, as failed, and pushes every assistant `tool_calls` entry as a `done` tool. Live, `withTool` leaves a tool `running` until its `tool` end event.
- The Next.js catch-all proxy (`frontend/app/api/[...path]/route.ts`) already forwards `POST` and `PUT`. It passes back only the response headers in `FORWARDED_RESPONSE_HEADERS` (`content-disposition`, `content-language`, `content-type`, `etag`, `last-modified`, `retry-after`). `X-Conversation-Id` is not among them, so `streamChat` in `lib/chat.ts` never sees it in the browser, although it reads it to call `onStored`.
- The `user_settings` row is created only by `PUT /api/settings/models`. A user who has not saved models has none.
- `DELETE /api/conversations/{id}` deletes without looking at the claim. `DELETE /api/me/content`, `DELETE /api/me`, `DELETE /api/demo/session`, and the demo cleanup loop (`delete_expired_demo_users` in `app/demo.py`) delete the user's rows without looking at running turns. With `background-turns`, a turn keeps running after its tab is gone, so a turn whose conversation is deleted goes on: its next `_store` and its `record_usage` insert rows that point at the deleted conversation, Postgres refuses them with a foreign-key error, and the round's usage is never recorded.

## Goals / Non-Goals

**Goals:**

- Stop ends the turn on the server, for the owner only, from any tab, and leaves a conversation the next message can use.
- A stopped answer is told apart from a failure, in the stream and in storage.
- What a stop stores never tells the model or the user that something did not happen when it may have.
- The cap uses the numbers the usage section already shows, so what the user sees is what is enforced.
- Raising or removing the cap never depends on a provider being reachable.

**Non-Goals:**

- Stop for `/compact` and for the offer before archive. Both are tied to their request; the compact dialog's Cancel already ends the draft.
- Estimated usage for a round cut by a server shutdown. It stays unrecorded, as today.
- A cap per conversation, per model, or per provider, and an instance-wide cap set by the operator (demo mode keeps its rate limits).
- Predicting the cost of the next turn and refusing it before the cap is reached.
- A cap month in the user's own time zone (decision 7).
- Locking the composer when the cap is reached. The refusal on send is the signal.
- Refusing embedding calls, the model test, or approving a connector action at the cap (decision 9).
- An account balance from the provider. Providers do not offer it.
- Telling a tab that already shows a conversation that another tab started a turn. It sees the turn when it loads the conversation, as in `background-turns`.

## Decisions

### 1. Stop is a POST on the running turn, and it answers at once

New route `POST /api/chat/{conversation_id}/stop`:

- Loads the conversation with `get_conversation` (owner-scoped; another user's and an unknown id both give 404 `not_found` with the same body). The registry entry's user id is also checked against the caller.
- Calls `RunningTurn.stop()`. The first call sets `stop_requested` on the turn; a later call (a second tab, a double click before `stopping` shows, or a retry after a first request that did reach the server) does nothing more. It cancels the task only when the turn is `interruptible` (decision 3) and no cancel was sent to it yet; the flag is read and the cancel sent in the same step. When the turn is not interruptible, it sees `stop_requested` at its next check and ends there (decision 3). It never waits for the task.
- Answers `204` at once in every case where the caller owns the conversation: stop sent, already stopping, past the turn's last check, or nothing running.

The chat does not act on the `204`. It keeps "Stopping…" until the stream's terminal event (decision 5), and that event is what unlocks the composer, as for every other end. `run` appends the terminal event before its `finally` releases the claim, the same order `background-turns` uses for `done` and `error`, so waiting in the route would protect no step the chat takes.

**A turn's task is cancelled at most once.** `RunningTurn` keeps `cancel_sent` and the reason of the one cancel (`stop` or `shutdown`). `background-turns`' lifespan exit goes through a new `RunningTurn.shutdown()`, which cancels only when no cancel was sent and `stop_requested` is not set. A turn that is stopping is not cancelled: it is only awaited within the same bound, and that wait (`asyncio.wait` with a timeout, not `wait_for`) sends no cancel of its own. A turn whose stop came outside a region reaches its next check within a few database calls, or the end of a built-in tool call (decision 3), and stops there. A second cancel would throw `CancelledError` into `_store_stopped` while it uses the session, and `run`'s `finally` would then commit and release the claim on the same `AsyncSession` while the store still runs on it, which SQLAlchemy forbids. `Turn` decides between the stopped store and the `answer_interrupted` store from the reason of the cancel it got, not from `stop_requested`, so a Stop that comes after a shutdown cancel leaves the shutdown path as `background-turns` has it.

The route never reads keys, so demo mode needs nothing new.

**Alternatives:** stop by dropping the stream (rejected: `background-turns` decided that leaving never stops a turn, and a second tab would have no way to stop it); answer `409` when nothing runs (rejected: a click that lands as the answer ends is not an error, and the stream already says how the turn ended); wait for the turn to end before answering, with a bound (rejected: the chat unlocks on the stream's terminal event, not on the stop's answer, so the wait protects nothing and adds a time bound, the case where it runs out, and the hardest tests); cancel again on every stop (rejected: see above); let shutdown cancel a turn that is stopping, and have `Turn` keep the stopped store's task so that `run`'s `finally` awaits it before it touches the session (rejected: it repairs the race after it happens, in a second place; one rule in the one class that sends cancels prevents it for both callers).

### 2. A stop has its own status and code; the stream ends with an `error` event

A stopped answer is stored as an `assistant` message with `status="stopped"` and `error_code="answer_stopped"`. The stream's terminal event is `error` with `{"code":"answer_stopped","message":"You stopped this answer."}`. `answer_stopped` is a stream-only code like `answer_interrupted`; it goes in `ErrorCode`.

The status says it is not a failure, for the frontend and for anyone reading the table. The code ties the stored message to the stream event, so a returning chat and a watching chat show the same thing. When the turn ended by a stop (the cancel `stop()` sent, or a check that found `stop_requested`, decision 3), `run` appends this terminal event and returns normally, so `finally` releases the claim as for any other end. A cancel from shutdown runs the existing `answer_interrupted` path unchanged.

**Alternatives:** reuse `failed` / `answer_interrupted` (rejected: the chat would say "This answer did not finish" for something the user chose); `cut` (rejected: `cut` means the length limit or a dropped connection); a new `stopped` SSE event (rejected: subscribers and the frontend end on `done` or `error`, and a third terminal event would touch each of them for no gain).

### 3. When a stop takes effect, and what is stored

`Turn` gets two flags that `RunningTurn` reads and sets: `interruptible` and `stop_requested`. The turn is interruptible only in two kinds of region, both in `Turn`'s own code:

- **The model stream.** `Turn` wraps the stream so the flag is set right before each wait for the next chunk, and right before `call.stream()` opens the call of a round after the first, and is cleared right after that await returns, in a `finally`, with no `await` in between. The events of a chunk are yielded with the flag cleared, so a cancel never lands in `run`'s code or in a store.
- **A connector call that may reach its server.** `_run_tool` sets the flag around `await provider.call(...)` and nothing else, and only for a call that decision 12 marks as one that may reach a remote server: a `ConnectorTools` reads tool, or an acts tool set to always allow that needs no card. A built-in call (`search_thoughts`, `propose_thought`) and an acts call that only writes a card are not regions. They make database queries and at most an embedding call, which has its own 10-second timeout, so they always run to the end.

**The check and the flag.** Before each region (every chunk wait, every later round's model call, and every connector call) and before every other tool call, the turn checks `stop_requested`. The check is synchronous and comes right before the flag is set, with no `await` between them. A stop that lands during any earlier await is then seen by the check, and a stop that lands after it finds the flag set and sends the cancel. Before a round after the first, the order is: the cap check (decision 10), then the stop check, then the region. When the check finds the stop, the turn stores the stopped answer and ends, as if the cancel had come.

Everything else runs outside a region: `record_usage` and `usage_warning` in `_note_usage`, the `_store` of each round, a built-in tool call, an acts call that writes a card, the commit in `_run_tool` described below, the cap check (decision 10), and every terminal store (`complete`, `cut`, `_store_failed`, the `tool_loop_limit` end, and the `spend_cap_reached` end). A cancel can never reach them. A stop that comes during one of them only sets `stop_requested`; the turn finishes that step, yields its events (a `usage_warning` notice, a `proposal` or `action` card, a `tool` end with a search's sources), and ends as stopped at its next check. The user does not press Stop again. A stop after the turn's last check (the final round's stream has ended, or a failure is being stored) finds no next check, so the turn keeps its own end: a complete answer stays complete, and a failed, `tool_loop_limit`, or `spend_cap_reached` end keeps its code, with no stopped answer added (spec scenarios "Stop after the answer is written" and "Stop while a failure is stored"). `run` picks the terminal event from how the turn ended, not from `stop_requested`. Asyncio runs one step at a time, so `stop()` reading `interruptible` and sending the cancel cannot interleave with the turn setting or clearing it.

`_store_stopped(state)` runs in the turn's own task, not under `asyncio.shield`: nothing cancels the task a second time (decision 1), and a shield would put a second task on the same session. Where the stop landed says what is committed, so the store needs no read-back:

- **In the stream** (the cancel came while a chunk was awaited or a later round's call was being opened, or the check before a chunk wait found the stop): the round in flight has no stored message and no usage row. Every earlier round, its tool messages, and its usage are committed.
- **At the check before a later round's call:** no call of that round was opened. Everything before it is committed.
- **At the check before a tool call, or in a connector call** (the cancel came in its `provider.call()`): the round's `tool_calls` message, its usage row, and the tool messages of the calls before this one are committed, each with what its provider wrote.

Then:

1. **Plain values first, then the rollback.** `Turn` saves the conversation id in `__init__`, and `_store` passes that id to `next_position`, not the `Conversation` instance. `_store_stopped` takes the ids and names of the round's calls and the position of its `tool_calls` message from `state` and from plain values the turn kept, never from ORM instances. It then calls `session.rollback()`, which drops anything a cancelled connector call added, and `await session.refresh(self.conversation)` before any store: a rollback expires every instance in the session, whatever `expire_on_commit` says, and reading an expired attribute on an `AsyncSession` raises `MissingGreenlet`. Every region and every check starts right after a commit, and a connector call only talks to its server, so the rollback normally drops nothing.
2. When the stop landed at the check before a tool call or in a connector call, store a `tool` message with `details: {"stopped": true}` for that call and for each call after it in the round. The call whose check found the stop, and every call after the one in flight, never started: their content is `"Not run: the user stopped the answer before this tool finished."`. The call in flight when a cancel came is always a connector call that may have run, and gets decision 12's text. The context sent next time then pairs every tool call with a result, as OpenAI-compatible APIs require.
3. When the stop landed in the stream, record the round's usage (decision 4). In every other case the round's usage is already recorded, or no call was made.
4. Store the stopped assistant message. When the stop landed at a tool call or at the check before a round's call, the text of the last round is already stored with its `tool_calls` message, so the stopped message has `content` null. When it landed in the stream, it holds the round's text so far (or `None`), and the round's tool-call pieces are not stored as calls: the model never finished asking for them. The names of those calls that already sent a `tool` start (`read_round` sends it as soon as the name arrives) go on the stopped message as `details: {"stopped_tools": ["search_thoughts"]}`, in order, so a reload shows the tool line the live chat showed (decision 5). `build_context` ignores `details`.

Closing the tool providers is not part of the stopped store; it stays in the turn's own `finally` (decision 12).

`_run_tool()` commits after `provider.call()` returns and before it yields any event for that call: the tool message plus whatever the provider added (a proposal from `BuiltinTools`, a `pending` `tool_actions` row from `ConnectorTools`) are committed, then the `proposal` or `action` event is yielded, then the `tool` end event. Neither the commit nor a built-in or card-writing call is a region, so a stop during them lets the call finish, the commit run, and both events go out, and ends the turn at the next check. A card the browser shows is then always stored, also when the commit itself fails, and every card that is stored is shown before the answer ends. The event order (`proposal` before `tool` end) is unchanged; only the commit moves before it. The rule sits in `_run_tool()`, not in each provider, so it covers both kinds of card.

`build_context` needs no change: a stopped message with text goes to the model like any assistant text; an empty one is skipped, as an empty failed one is today.

**Alternatives:** cancel the task wherever it is (rejected: a cancel can then land in any commit, so every commit needs a helper that a cancel cannot cut, every terminal store a flag that turns Stop off, the stopped store must read back what got committed to avoid counting usage twice, a card committed by a cut commit needs a late event, and each of those needs a race test with a blocked commit; cancelling only inside the stream and connector calls makes all of it unnecessary, and a stop anywhere else waits only for a few database calls); make every tool call a region, built-in ones too (rejected: a cancel could then land mid-embedding or mid-SQL in a search or proposal, so the stopped store would have to copy embedding usage rows across the rollback, find rows that autoflush had already written, recover a connection the cancel broke, and tell the model "not run" for a search that was embedded and billed; a built-in call is short and bounded by its embedding timeout, and Stop is for long streams and slow connector calls); check `stop_requested` before the cap check (rejected: `cap_state()` awaits a query, and a stop that lands then would find the flag clear and the check already passed, so the next round's call would start after the stop); a flag the turn polls between rounds and tools, with no cancel (rejected: it could not stop a long stream or a 30-second connector call, the main reasons to press Stop); ignore a stop that comes outside a region (rejected: the user would have to press Stop again; `stop_requested` makes it take effect at the next check); cancel at once and roll back the whole turn (rejected: the spec keeps what was produced, and the user paid for it); skip the rollback (rejected: it costs nothing when the session is clean, and it keeps anything a cancelled connector call left in the session out of the stopped store's commit); skip the stopped message when the round's `tool_calls` message is stored (rejected: the "You stopped this answer." note after a reload comes from that message); drop the names of tools cut off mid-call (rejected: the live chat showed them, and a reload would lose them); commit inside each provider (rejected: the rule would have to be repeated in every provider, and a new one could forget it).

### 4. A stopped round's usage is recorded from what was reported, else estimated

A provider with `stream_usage: final_chunk` sends usage only in the final chunk, which a stopped stream never reaches. Recording nothing would hide spend from the usage graph and from the cap. So the stopped round is recorded through `record_usage`:

- When `state.prompt_tokens` is set (a provider with `stream_usage: incremental` reported counts before the stop), the prompt tokens are the reported ones and the completion tokens are the larger of the reported count and `estimate_text_tokens(text and tool-call arguments received)`. The last report can trail the text that arrived after it.
- When nothing was reported, `prompt_tokens = estimate_tokens(context sent)` and `completion_tokens = estimate_text_tokens(text and tool-call arguments received)`.
- A provider with `stream_usage: none` keeps tokens unknown, as today.

The cost comes from the model's listed prices. A stop in the stream comes before the round's `record_usage`, and a stop anywhere else comes after it (decision 3), so a round is never recorded twice.

**No await in a turn reaches the model list.** `_note_usage`, `_suggest_compact`, and `record_usage` today await `call.info()`, which fetches the provider's model list on a miss in the five-minute cache. A stop would then wait for that fetch between regions, and the stopped store's own `record_usage` could hang on the provider the user is stopping, past the shutdown bound. So `Turn` takes the `info` that `POST /api/chat` already resolved with `model_info()` for `check_room`, and uses it for the meter, the compact suggestion, and every usage row of the turn. `record_usage` gains an optional `info` argument; the turn always passes it, and only a caller that passes none (`/compact`, the offer, the model test) still calls `call.info()`. When the route could not read the list, `info` is `None` and the turn's rows have unknown cost, as today when the list cannot be read.

**Alternatives:** record nothing (rejected: a user stops an answer most often when it is long, which is when spend matters); a cache-only lookup on the stopped path that falls back to unknown cost (rejected: the rounds before the stop would still wait on the fetch, and two paths would read one value); keep `call.info()` in the turn (rejected: see above); always estimate (rejected: it throws away a count the provider reported); an `estimated` column on `usage_events` (rejected: every cost in the report is already labelled an estimate; a column needs a migration and a UI for little); count reasoning tokens (not possible: the stream's reasoning field is not read).

### 5. The chat's Stop button

`Composer` gets `onStop` and `stopping`. While a turn is being sent or followed, it shows Stop in place of Send. It is enabled once the chat knows the conversation id and the stream has started (the POST answered, or the follow stream opened). Before that the turn is not in the registry yet. `/compact` passes no `onStop`, so its dialog keeps Cancel.

Pressing Stop calls `stopTurn(conversationId)` in `lib/chat.ts` (`apiFetch`, `POST`, `204`), sets `stopping`, and does not abort the stream. The stream's terminal `error` event with `answer_stopped` sets the answer to a new `stopped` state, ends the thinking indication when no text had arrived, and ends `answering` in every tab, because every tab reads the same log. `stopping` stays until the stream's terminal event, whichever it is: the `204` does not clear it. A stop that did nothing (the turn was past its last region, decision 3, or had already ended) is followed by `done` or another `error`, such as `spend_cap_reached` or a provider code. That event clears `stopping`, unlocks the composer, and shows the answer as the event says: complete with no stopped note, or the error. A failed stop request shows "The answer could not be stopped. Try again." under the answer and clears `stopping`.

`ToolIndication.state` gains `stopped`, shown with no spinner as "Stopped before it finished". On the `answer_stopped` event every tool still `running` becomes `stopped`. `fromStored` reads `details.stopped` on a `tool` message and marks the tool of the same `tool_call_id` as `stopped`, and adds one `stopped` tool for each name in a stopped message's `details.stopped_tools` (a call cut off while the model was still sending it, decision 3 step 4). A reload then shows what the live chat showed. A search or proposal that finished keeps `done`.

`fromStored` maps `status === "stopped"` to the `stopped` answer state with no error, before its failed check. `message-list.tsx` shows "You stopped this answer." in muted text, not an alert, with the text, tools, sources, and cards kept. A stopped answer is not "unfinished" for the resend shortcut in `send`: sending the same text again sends a new message and keeps the stopped answer as it is. An answer that ended at the spend cap during its turn follows the same rule (decision 10). When the POST stream drops with no terminal event and the follow route answers `204` (`background-turns` decision 2), the reloaded detail decides: a last assistant message with `status: "stopped"` shows as stopped, with its note, and not as cut short, also when the stop came from another tab.

**Alternatives:** abort the stream on Stop and reload (rejected: the second tab would still need the event, and the reload races the store); clear `stopping` on the `204` (rejected: the answer has not ended yet, and the composer would unlock while the turn still holds the conversation); clear `stopping` only on `answer_stopped` (rejected: a stop that did nothing is followed by another terminal event, and "Stopping…" would never clear); on `answer_stopped`, drop tools whose call was never stored, so the live chat matches a reload (rejected: the user saw the tool start, and it vanishing would hide that the model began to use it); Stop as a separate button next to Send (rejected: two buttons that never both work); show a cut-off tool as `done` (rejected: "Searched your thoughts" for a search that never ran is false); a separate `not_run` state (rejected: a connector call may have run, decision 12, so one neutral label fits both).

### 6. The cap is stored on `user_settings` and saved on its own route

Two nullable columns on `user_settings`: `cap_unit` (`String(8)`, `usd` or `tokens`) and `cap_amount` (`Numeric(18, 6)`). Null means no cap. One Alembic migration adds them.

`PUT /api/usage/cap` takes `{"cap": {"unit": "usd" | "tokens", "amount": > 0} | null}`, validated like the warning (`max_digits=18, decimal_places=6`), and answers the cap state. `GET /api/usage` gains `cap: {unit, amount, reached, resets_on} | null`, where `resets_on` is the first day of the next month in UTC; in December that is 1 January of the next year. Both use `get_current_user`, so they only ever touch the caller's row. When the caller has no `user_settings` row yet (a user who has not saved models, or a new demo visitor), `PUT /api/usage/cap` creates it with the cap and every other column null, as `PUT /api/settings/models` does; `{"cap": null}` with no row answers `{"cap": null}` and creates nothing. `GET /api/usage` reports `cap: null` for a user with no row.

The usage section gets a "Monthly spend cap" form beside the month total: a unit select (No cap / Estimated dollars / Tokens), an amount, and its own Save. Under it: "New chat messages are refused once this month's usage reaches the cap. It resets on <date> (UTC). Calls with unknown cost count in tokens only. Deleting your usage history makes the cap count from zero again for this month." In demo mode (`useDemo()` set) the last sentence is left out: demo mode offers no delete choice, and "End demo" deletes everything. The month total shows "Spend cap: $5.00. Reached this month." or "Not reached."

The "Delete usage history" confirmation in `delete-data-settings.tsx` gets one fixed sentence at the end of its `deleted` text: "If you set a monthly spend cap, it counts from zero again for this month." The confirmations stay fixed strings; the dialog reads nothing when it opens.

**Alternatives:** save the cap with the warning in `PUT /api/settings/models` (rejected: that save checks every loadout model with its provider, so an expired demo key or an unreachable provider would stop a user from raising their cap exactly when they need to); a separate `spend_caps` table (rejected: one value per user, and `user_settings` already holds the warning); keep a separate running sum that survives deleting the history (rejected: the history is the record the user asked to delete, and a hidden copy of it would defeat that); read the cap with `getUsage()` when the delete dialog opens and add the sentence only when a cap is set (rejected: a loading case and a fallback for a failed read, for a warning the cap form already gives; one fixed sentence says the same); refuse the cap save until models are saved (rejected: the cap would then depend on the model save, which decision 6 keeps it apart from).

### 7. What counts: every usage row of the calendar month in UTC

The cap compares `month_totals()`, the same function the warning and the usage section use: all `usage_events` rows of the user since the first of the month at 00:00 UTC, every kind. A new `cap_state(session, user_id)` in `app/chat/usage.py` returns `None` without a cap, else the cap, the month's sum in its unit, and `reached` (sum ≥ amount). Rows of a deleted conversation keep counting: their `conversation_id` is set to null, not deleted.

`cap_state()` reads `cap_unit` and `cap_amount` fresh on every call, with `select(UserSettings.cap_unit, UserSettings.cap_amount).where(UserSettings.user_id == user_id)`, never through the `UserSettings` instance. The turn runs on the session the route opened, and the route's `temperature_for()` (`app/chat/loadout.py`) has already loaded the user's `UserSettings` row into it. With `expire_on_commit=False` (`app/db.py`), `session.get(UserSettings, ...)` or `select(UserSettings)` would hand back that cached instance on every round, so a cap the user saves from another tab while the turn runs, which is when a user watching spend sets one, would be ignored for the rest of the turn. Selecting the two columns returns rows, not instances, so the identity map is not consulted.

**Alternatives:** the user's local month (rejected: no zone is stored per user; `thought-dates` sends the zone per request, so the month would move with each request, and the usage section shows UTC days and a UTC month); only chat kinds (rejected: embeddings and tests are paid with the same keys); read the row with `session.get` as `usage_warning` does (rejected: it returns the instance cached by `temperature_for()`, see above); `select(UserSettings).execution_options(populate_existing=True)` (rejected: it also works, but it overwrites the cached instance's other attributes in the middle of a turn, and the two columns are all the check needs).

### 8. Unknown prices count as nothing in dollars, and the cap still refuses every model

A call with unknown cost adds nothing to a dollar cap, as it adds nothing to the dollar total in the usage section. A token cap counts its tokens when they are known. Once the cap is reached, every new turn is refused, whatever its model's price. The cap form says that unknown-cost calls are not counted in dollars, and the usage section already counts them.

**Alternatives:** guess a price for unlisted models (rejected: an invented number in a spend limit); exempt unknown-price models at the cap (rejected: a model whose provider lists no price is not free, so it would escape the cap); refuse unknown-price models whenever a dollar cap is set (rejected: local models are free, and that would choose for the user which models they may use).

### 9. Where the cap is checked

- **Before a turn.** In `POST /api/chat`, after the user message is stored and `_ensure_model` runs, and before `model_info` or any provider call: `cap_state()`; when reached, raise `spend_cap_reached()`: HTTP 409, message "Your monthly spend cap of $5.00 is reached (this month so far: $5.12, estimated). Raise or remove it in Settings to keep chatting. It resets on 1 December (UTC)." In December it says "It resets on 1 January (UTC)." The token form names tokens. The message stays stored and the error carries `X-Conversation-Id`, as other refusals after the store do. For the first message of a new conversation, the conversation was created and committed with the message, so the browser needs that id to send to it again. The Next.js proxy drops every response header not in `FORWARDED_RESPONSE_HEADERS`, so this change adds `x-conversation-id` to that list. It is the caller's own owner-scoped id, not a secret, and `Set-Cookie` and the other headers stay dropped. This also fixes the other refusals after the store, which carry the header today and lose it in the proxy.
- **Connector actions expire only after the check passes.** This change moves the expiry of `pending` and `failed` `tool_actions` rows (from `mcp-connectors`) out of the claim transaction to just before `turn.open()`, after the cap check and `check_room`, and commits it on its own. A send refused at the cap then leaves the cards approvable. A turn that has started has always committed the expiry, so a stop in its first round, whose rollback (decision 3 step 1) drops only what the session holds uncommitted, cannot make the old cards approvable again. When `turn.open()` then fails (the provider refuses or fails the first model call, for example `provider_key_rejected` on a 401 or `provider_unreachable`), the cards stay expired, as in `mcp-connectors`, where every send that takes the claim expires them: the message was sent to the model, so it counts as a sent message. The claim is held from before the expiry until the turn ends, so an approval still cannot overlap a turn. Every send refused before the expiry keeps the cards approvable, not only one refused at the cap: `model_not_set`, `too_many_tools`, a missing key, and a full context are refused there too. `mcp-connectors`' requirement already says an action is approvable until the next turn starts, but its scenario "Approve after moving on" reads as if any sent message expires it, so this change modifies that requirement to say where the line is: a message refused before its first model call is sent does not expire them, and a message whose first model call the provider refuses or fails does.
- **Before `/compact`.** In `compact()`, after `_ensure_model`, the same check. `compact()` stores no user message and sets no `X-Conversation-Id`, so a refused `/compact` changes nothing in the conversation: its error path rolls back and releases the claim, as for any other `/compact` refusal.
- **Between rounds.** In `Turn.events()`, before each round after the first, when a cap is set. Decision 10.
- **The offer.** `offer_proposal()` returns a held proposal as now. Where it would ask the model, at the cap it returns `None`, so archive goes ahead with no offer. This adds an exception to conversation-agent "The offer before an action may propose nothing", which this change modifies from `thought-status`'s text (itself built on `thought-appending`'s). `/compact` is refused by its own check after the offer.
- **Not checked:** `embed_texts()` and its callers, the model test, proposal confirm, approving or declining a connector action (it calls the connector's server, not a model), and every read.

HTTP 409, like `model_not_set`: the request is valid but the user's settings stop it, and the fix is in Settings.

**Alternatives:** check before storing the user message (rejected: every other refusal after the claim keeps the message, and the resend shortcut avoids a duplicate); keep the action expiry in the claim transaction (rejected: a user at the cap who types a message would lose their pending action cards although no turn ran); refuse embeddings too (rejected: they cost a small share of a chat call, and refusing them would fail a confirm's indexing or turn a search into a words-only search with no clear cause); refuse the model test (rejected: a test is two short calls and helps the user pick a cheaper model); refuse approving an action (rejected: it makes no model call, and the user already saw the card); leave the moved expiry pending until the turn's first commit (rejected: a stop before `record_usage` of the first round rolls it back, and the old cards become approvable after a turn started); commit the expiry after `turn.open()` returns (rejected: the model call is then open while the commit runs, and its failure path would also have to close the call; a failed open is a send like any other); read the conversation id from the response body in the browser (rejected: `streamChat` already reads the header for every refusal after the store, and the proxy is the one place that drops it); HTTP 402 (rejected: it reads as paying this app) or 429 (rejected: it means wait and retry soon).

### 10. A turn that crosses the cap finishes the call in flight, then stops

Before starting round `n > 0`, and before its stop check (decision 3), the turn calls `cap_state()`. The stop check comes after it because `cap_state()` awaits a query: a stop that lands during that query is then still seen before the region starts, and no model call opens after it. When reached, it sets `error_code="spend_cap_reached"` on the last stored assistant message (its tool calls already have their results) and commits, outside any region, so a stop then leaves this end as stored; then it raises `spend_cap_reached()`, which `run` turns into the terminal `error` event, the same way `tool_loop_limit` works. The final round crossing the cap needs nothing: the answer is complete and the next send is refused.

`fromStored` already shows any `error_code` as a failed answer with its error class. For `spend_cap_reached` it uses the message "Your monthly spend cap was reached during this answer. Raise or remove it in Settings to keep chatting." It names no amount: the stored message holds only the code, and the cap may have changed since. chat-interface "Errors are shown in the chat" asks only a refused message to name the cap; an answer that ended at the cap says the cap was reached, live (the backend's message, which names it) and after a reload (this text). The chat's error component shows a `SpendCapAlert` (title "Monthly spend cap reached", the message, and a "Go to usage settings" link to `USAGE_SETTINGS_HREF`).

The compact dialog shows the same alert. `CompactState`'s `failed` step gains an optional `code`; `runCompact()` keeps the `ApiError`'s code (and the code of a stream `error` event), and `compact-dialog.tsx` renders `SpendCapAlert` in the failed step when the code is `spend_cap_reached`, in place of the plain text. Other `/compact` failures show as today.

Sending the same text again after an answer that ended at the cap during its turn is a new message, as after a stop (decision 5). That answer's rounds are stored and the backend's last message is the assistant one, so the backend stores the resent text as a new user message anyway; `retry()` would instead clear the kept tools, sources, and card in the live chat, and a reload would show the message twice. `AnswerMessage` gains `endedInTurn`, set when the stream's `error` event is `spend_cap_reached` and by `fromStored` for a stored assistant message with that code, and `send()` does not take the resend shortcut for such an answer. A send refused at the cap before any turn (the `409` on `POST /api/chat`) has no stored answer: the backend's last message is the user message, so it stays "unfinished", and the resend reuses the stored message and shows it once.

**Alternatives:** cut the stream when a chunk would cross the cap (rejected: the tokens are not known until the final chunk, the cut text is paid for anyway, and the check would run on every chunk); let the turn run to its end (rejected: up to `tool_rounds` model calls past the cap); keep the resend shortcut for an answer that ended at the cap during its turn (rejected: it wipes what the user paid for in the live chat and stores the message twice); treat every `spend_cap_reached` answer as finished, also a refused send (rejected: the live chat would show the resent message twice while the backend stores it once); send `/compact` refusals through `ChatError` (rejected: the dialog is already open and owns the failed step); show only the backend's text in the dialog (rejected: the user would have no link to where the cap is changed); store the cap's text on the answer so a reload names it (rejected: the cap shown would be the one at the time, which may since have been raised, and the stored message would need a new field for one line).

### 11. Demo mode

Nothing changes for demo mode. A demo visitor is a user like any other; their cap is saved (creating the `user_settings` row when the visitor has none yet, decision 6), enforced, and deleted with their data when the session expires. Stop needs no key.

### 12. Stop and connector tools

A connector call can reach its server before the stop: cancelling the task only drops the reply, and a remote write such as `calendar__create_event` is not undone. So `Turn` records which tool call is in flight and whether it may reach a server: true for a `ConnectorTools` call that needs no approval (a reads tool, or an acts tool set to always allow), false for a built-in tool and for an acts call that only writes a card. Only a call marked true is a region (decision 3); the others always run to the end. When the cancel came in that call's `provider.call()`, its tool message in `_store_stopped` step 2 is "Stopped while calendar__create_event was running. It may have run; check before running it again.", with `details: {"stopped": true}`. Calls after it in the same round never started and get the "Not run" text, as does a call whose check found the stop before it started.

A `tool_actions` row is only ever `pending` inside a turn: approvals run outside turns and are refused while one runs. With decision 3's commit before the `action` event, a stop while an acts call writes its card, or after it returned, lets the commit and the card go out first and leaves the row `pending` and approvable until the next turn starts: that call is not a region, so no cancel lands in it. No row is left `running` by a stop.

`ConnectorTools.aclose()` stays in the turn's own `finally`, as `mcp-connectors` decision 9 has it, and runs after `_store_stopped` returns. It must run in the turn task: the SDK's `streamablehttp_client` and `ClientSession` are `anyio` context managers whose task groups were entered in that task, and exiting them from another task raises "Attempted to exit cancel scope in a different task than it was entered in". The stopped store also runs in the turn task (decision 3), so no step of a stop moves to another task. A turn's task is cancelled at most once (decision 1), so the `finally` is reached; the close is wrapped in `anyio.CancelScope(shield=True)` so a shutdown cancel that lands while a turn that ended on its own is closing cannot skip it.

**Alternatives:** store "Not run" for every cut-off call (rejected: the model would be told a write did not happen and may do it again); ask the server whether the call ran (rejected: MCP has no such request); wait for the connector call to finish before stopping (rejected: a call can take up to `call_seconds`, 30 seconds, and Stop should end the answer now); close the connector in a task of its own, such as under `asyncio.shield` (rejected: it runs in another task, which the SDK's `anyio` context managers refuse).

### 13. Deleting stops the user's running turns first

A turn runs on after its tab is gone (`background-turns`), so a user can delete a conversation, their content, or their account, or end their demo session, while a turn still spends their key. Deleting first would leave a turn nobody can stop (the Stop route's `get_conversation` answers 404 once the conversation is gone), and the round's usage row would be refused by the foreign key, so spend would slip past the cap and break usage-tracking's "Deleted conversation" scenario.

New `stop_turns(user_id, conversation_id=None)` in `app/chat/running.py`: it calls `RunningTurn.stop()` on each of the user's running turns (or on the one turn of that conversation), then awaits them with `asyncio.wait` and the shutdown bound, sending no cancel of its own (decision 1). Each turn then ends through its stopped store, which commits the stopped answer and its usage row (decision 4) while the conversation still exists. The delete that follows keeps those usage rows, with `conversation_id` set to null by the existing `ondelete`.

- `DELETE /api/conversations/{id}` calls `stop_turns` for that conversation, then `claim_turn(..., busy=conversation_delete_busy)`, which answers 409 `conversation_busy` when a turn still holds the claim after the bound, then deletes. The claim also keeps a send from another tab from starting a turn between the wait and the delete, and it covers a message that holds the claim but is not in the registry yet (below).
- `DELETE /api/me/content`, `DELETE /api/me`, and `DELETE /api/demo/session` call `stop_turns` for the user, then claim every conversation of the user in the delete's own transaction: `UPDATE conversations SET turn_started_at = :stamp WHERE user_id = :u AND (turn_started_at IS NULL OR turn_started_at < :stamp - TURN_CLAIM_TIMEOUT)`, then `SELECT count(*) FROM conversations WHERE user_id = :u AND turn_started_at IS DISTINCT FROM :stamp`. When that count is not 0, the delete rolls back and answers 409 `conversation_busy`, and nothing is deleted; the user tries again. Otherwise the delete goes on in the same transaction and removes those rows anyway, so the claim takes no lock beyond the rows the delete already locks.
- The demo cleanup loop does the same for an expired visitor and skips one whose claim it cannot take until its next pass. Once the turn has ended, the demo key held in its task's memory is dropped (`background-turns` decision 6).

**Why the bulk deletes claim.** `background-turns` adds a turn to the registry only after `turn.open()` returns. Before that, `POST /api/chat` holds the claim and runs `_ensure_model`, the cap check, `model_info()` (which can fetch the provider's model list), `check_room`, the action expiry commit, and the opening of the first model call. That can take many seconds while the chat shows "thinking", and "End demo" sits in the header of that same page. `stop_turns()` finds nothing then. Without the claim, the delete would go ahead, the POST would open or stream the model call with the user's key (for a demo visitor, after they ended the session), and its first `_store` and `record_usage` would fail on the foreign key, so the spend would go unrecorded and past the cap. The claim sees that message as busy. The count after the update, not a count taken before it, also sees a conversation another tab created and claimed in between.

**The busy messages.** `conversation_busy()` keeps its text for a send ("This conversation is still answering another message. Wait for it to finish."). Deletes get their own text with the same code, from two new helpers in `app/errors.py`: `conversation_delete_busy()`, "An answer in this conversation is still running. Try deleting again in a moment.", for `DELETE /api/conversations/{id}` (`claim_turn` gains an optional `busy` argument, the error it raises, defaulting to `conversation_busy`); and `turns_busy()`, "An answer is still running. Try again in a moment.", for the bulk deletes. Neither says "being stopped": a message still being opened is not stopped by `stop_turns`, and the next try stops it once it is in the registry. The sidebar's and `/delete`'s `DeleteDialog` show the error's message as they are, and `DeleteDataSection` shows `ApiError.message`, so the frontend needs no code change; the "Delete content" and "Delete account" dialogs stay open with the message. "End demo" in `demo-bar.tsx` keeps its fixed "Could not end the demo. Try again.", which fits.

**Alternatives:** refuse a conversation's delete with 409 while its turn runs and let the user press Stop first (rejected: it still leaves the bulk deletes and the demo expiry, and a user who deletes means to stop); cancel the task like a shutdown (rejected: it stores `answer_interrupted` for something the user chose, and a cancel can land in a store, decision 3); delete first and let the turn fail (rejected: its usage is lost and a demo key keeps being used after the visitor ended the session); for the bulk deletes, check only the registry after `stop_turns` (rejected: it misses a message that holds the claim before `turn.open()` returns, see above, and a send from another tab between the wait and the delete); compare the update's row count with a count of the user's conversations taken before it (rejected: a conversation created and claimed by another tab between the two statements is in neither, and the delete would remove it under a running send); add the turn to the registry before `_ensure_model` (rejected: it changes `background-turns`' rule that errors before the first byte stay ordinary responses, and the registry would hold turns that never open); reuse `conversation_busy()`'s text for deletes (rejected: "still answering another message" makes no sense in the "Delete content", "Delete account", or a conversation's delete dialog); one delete text for both (rejected: the conversation's dialog can name the conversation, the bulk dialogs cannot).

### 15. Build note: the migration sits on `thought-status`' head

### 16. Build note: `cap_state()` and the cap's wire shape

`cap_state(session, user_id, moment=None)` returns `None` without a cap, else a frozen `CapState(unit, amount, used, reached, resets_on)`: `used` is the month's sum in the cap's unit (a `Decimal` of estimated dollars, or of tokens), from `month_totals()` as decision 7 says, and `resets_on` is `next_month_start(moment)`, the first day of the next month in UTC (1 January after December). `moment` defaults to `utc_now()`; `GET /api/usage` passes the `now` it reports the month with, so the month total and the cap state agree. `CapState.payload()` gives the wire shape `{unit, amount, reached, resets_on}`, where `amount` is an integer for tokens and a float for dollars, as `threshold_payload()` does for the warning; `used` stays server-side for the refusal message of task 2.1. The request model `SpendCap` copies `UsageWarning` (`unit: "usd" | "tokens"`, `amount > 0`, `max_digits=18`, `decimal_places=6`), and `cap` is a required key whose `null` removes the cap. `PUT /api/usage/cap` answers the state read with `cap_state()` after its commit.

### 17. Build note: the refusal's text and where the checks sit

`spend_cap_reached(state)` in `app/errors.py` takes the `CapState` of decision 16 (typed by a small protocol, so `errors.py` imports nothing from `app.chat`). The cap and the month so far are written as the usage settings write a threshold (`formatThreshold` in the frontend): dollars with at least 2 and at most 6 decimals and thousands separators (`$5.00`, `$0.001`, `$1,234.50`), tokens as a whole number with separators (`2,000,000 tokens`, `1 token`). The month so far uses the same rule, so a sum such as `$5.000011` shows its last digits rather than rounding down to the cap. The reset day is written `1 December`, with an English month name from a fixed table (not `strftime`, which follows the process locale). The check before a turn is one helper, `_check_cap()` in `app/routers/chat.py`, called after `_ensure_model` in `chat()` and in `compact()`. The check between rounds is `Turn._check_cap(last_answer)`, called before `call.stream()` of every round after the first; the stop check of task 3.1 goes after it, as decision 10 says.

**Alternatives:** round the month so far to cents (rejected: `$5.00` beside a `$5.00` cap reads as not reached when the sum is `$4.999`); build the message in `usage.py` (rejected: every other refusal text lives in `errors.py`).

### 18. Build note: a refused message no longer moves the conversation on

`mcp-connectors`' approve route expires a pending action when `moved_on()` (`app/chat/actions.py`) is true. It was true once any user message came after the action, so with decision 9's moved expiry a send refused at the cap or by `check_room`, which still stores the user message, would have expired the card at approve time anyway, and "Approve after a refused message" could not pass. `moved_on()` is now true only when an assistant message comes after the first user message after the action: a turn ran and answered (also one that ran while connectors were off, which expired nothing, the case the check was for). A message refused before any model call stores no answer, so the card stays approvable. A first call the provider refuses stores no answer either, but that send expired the card through the moved expiry already. `tests/test_connector_actions.py::test_a_later_user_message_expires_an_action_no_turn_expired` now stores an answer after the later message.

**Alternatives:** keep `moved_on()` as it was (rejected: it undoes decision 9 for every refused send); drop `moved_on()` (rejected: a turn that ran while connectors were off would leave an old card approvable after the conversation moved on).

### 19. Build note: the turn's context reads the open cards as expired

The moved expiry runs after `build_context()`, which writes each finished action's outcome note for the model. Before the move, the turn's context already read the open cards as expired ("The user did not approve … before the conversation moved on. It did not run."). To keep that, `build_context()` gains `actions_expire`, and `outcome_note(action, expiring=True)` reads a `pending` or `failed` action as the `expired` one the turn makes it, without changing the row before the checks pass. The chat route passes it; the context meter's `build_context()` call in the conversations route does not.

**Alternatives:** set the loaded rows' status in memory before `build_context()` (rejected: an autoflush could write it inside the transaction a refusal then rolls back, and it holds a row lock across `model_info()`); build the context again after the expiry (rejected: twice the work, and `check_room` would have measured the other one).

### 20. Build note: the chat stops marking cards expired on a stored refusal

`runAnswer()`'s `onStored` callback in `components/chat/chat.tsx` marked every waiting card expired when a refusal had stored the message, because the server expired them in the claim transaction. With decision 9 that is false for every refusal before the first model call, so the callback now only adopts the conversation id. A refusal from the provider on the first call did expire the cards; the chat cannot tell it from the others by its code (`context_full` comes from both `check_room` and the provider), so such a card shows as waiting until its Approve answers `409 action_expired`, which marks it expired as before. The first event of a turn that started still marks them expired (`startingTurn`). `action-card.test.tsx` now expects a card to stay waiting after a stored `too_many_tools` refusal.

**Alternatives:** expire the cards on a stored refusal with a provider error code (rejected: the codes overlap, see above); reload the conversation's actions after every stored refusal (rejected: one more request for a case the approve answer already settles).

### 21. Build note: where Stop lives in the built `background-turns` code

`app/chat/running.py` gains `TurnControl` (`interruptible`, `stop_requested`, `cancel_reason`), which `Turn` owns and `running.start(..., control=turn.control)` shares with the registry entry; the argument is optional, so the registry tests that drive `start()` with a script still work. `RunningTurn` gains `control`, `cancel_sent`, `stop()`, and `shutdown()` as decision 1 describes. The module-level `shutdown()` stays the lifespan's entry point: it calls each turn's `shutdown()` and then `asyncio.wait` on the tasks and the settle steps. The bound is `running.STOP_WAIT_SECONDS` (5 seconds), read at call time, so a test can lower it; `stop_turns()` uses the same bound, and `app/main.py` no longer has its own `TURN_SHUTDOWN_TIMEOUT`.

Decision 1 says `run` appends the terminal event before its `finally` releases the claim. The built `background-turns` does the opposite: `_settle` runs the route's settle step (which releases the claim), removes the registry entry, and only then ends the log. The build keeps that order. It is what lets a message sent right after the `answer_stopped` event be answered instead of refused as busy (task 3.4 checks this).

The route's `events()` wrapper closes the providers in the turn's own task, inside `anyio.CancelScope(shield=True)` (decision 12). The stop route loads the conversation owner-scoped, closes its session, and calls `RunningTurn.stop()` only when the entry's user id is the caller's.

**Alternatives:** a reference from `RunningTurn` to `Turn` (rejected: the registry would import the turn and its database code for three flags); move the terminal event before the settle step (rejected: see above).

### 22. Build note: how the turn knows where a stop landed

A check that finds `stop_requested` raises an internal `StopRequested`, which `Turn.events()` catches before its generic `except Exception`, so it never reaches `_store_failed`. A `CancelledError` whose `cancel_reason` is `stop` calls `asyncio.current_task().uncancel()` first, so the stopped store's awaits and the anyio cancel scopes after it are not cut, then takes the same path; any other cancel keeps the `answer_interrupted` path. Both paths store the stopped answer and raise `answer_stopped()`, which `_run` turns into the terminal event, and set `_end_stored`.

The turn keeps a `StopPoint` of plain values: `stream`, `round` (the check before a later round's call), or `tool`, with the round's call ids and names, the index of the call being run, and `in_flight` while a connector call that may reach its server is awaited. The stopped store reads it, and the round's `RoundState`, before its rollback. The guarded stream (`_guarded`) and `_interruptible()` hold the check, the flag, and the await together. A cancel while a later round's call is being opened counts as a stop in the stream, as decision 3 says: its row is recorded with the estimated prompt tokens and the completion tokens of what arrived (none). "The context sent" is `estimate_tokens(self.context, self.tools)`, which is what the request carries, and "text received" is the round's text plus the arguments of its tool calls (not their names).

**Alternatives:** record nothing for a cancel during the opening of a round (rejected: the request may have reached the provider, and decision 3 counts it as in the stream); estimate the prompt without the tool definitions (rejected: they are sent and billed).

### 23. Build note: closing the stream, the info, and the positions

`ModelCall.stream()`'s `chunks()` closes the provider response in a `finally`, and a stop found by a check calls `aclose()` on the round's chunks, so the response ends in both paths (a cancel already closes it through the SDK stream's own `finally`). `Turn` takes `info=` from the route; `record_usage` gains a keyword `info` whose default is a module sentinel, so a passed `None` (the list could not be read) records an unknown cost without calling `call.info()`, and callers that pass nothing (`/compact`, the offer, the model test) still fetch it. `next_position()` takes the conversation id; `Turn` keeps `conversation_id` from `__init__`. The `ToolProvider` protocol gains `reaches_server(name, turn)`: `BuiltinTools` answers false, `ConnectorTools` answers true for every call that needs no approval.

### 24. Build note: the deletes claim in their own transaction

`claim_user_turns(session, user_id)` in `app/chat/conversations.py` runs decision 13's update and count, and rolls back and raises `turns_busy()` when the count is not 0. `stop_and_claim()` in `app/user_data.py` commits the request's read transaction, awaits `running.stop_turns(user_id)`, then claims. The delete helpers already delete and then commit, so called after the claim they delete and commit in the claim's transaction; they need no split. The demo cleanup reads the expired users' ids, skips a visitor whose claim fails, and deletes by id (`delete_user_by_id`): the rollback of a failed claim expires every loaded `User`. `DELETE /api/conversations/{id}` commits its read, stops that conversation's turn, and claims with `busy=conversation_delete_busy`.

### 25. Build note: what the Stop tests observe

A task's `cancel` cannot be replaced on an `asyncio.Task` instance, so the tests count cancels with a task factory that creates a `Task` subclass counting its `cancel()` calls (`tests/stop_helpers.py`). `AsyncSession.commit` is patched to wait while the session holds the rows a test names. The fake provider records each streamed body and whether it was closed, and can hold its model list. The incremental-usage checks copy the provider fixture with Nebius's `stream_usage` changed, so `valid.yaml` keeps its two presets.

The MCP SDK used here gives the client no session id, so closing a connector session sends no HTTP `DELETE`. Task 3.2's "the fake server sees the session end" is therefore checked as: the client session the turn opened ran its `aclose()` in the turn (its background task is gone) and the test server holds no open connection from it. The test server gained a hold for `create_event`, the method of each request, and its count of open connections.

### 26. Build note: the cap form

The form sits under the month total in `UsageSection` as its own `SpendCapForm`, with a unit select ("Spend cap unit": No cap / Estimated dollars / Tokens), an amount ("Spend cap amount"), and "Save cap". It starts from the cap the first report loaded and keeps what the user typed while the report reloads (a period change or a deleted history); a save puts the answered cap state into the report, so the month total's "Spend cap: …" line follows at once. An empty, zero, or unreadable amount shows "The spend cap needs an amount above zero." and sends nothing, as the warning field in the model settings does; a backend error shows its message and keeps the input. The reset date is written with its year ("It resets on 1 January 2027 (UTC)."), from `cap.resets_on`, or, with no cap set, the first day after the report's month: in December the year changes, and the form is the place the user plans from. The backend's refusal keeps "1 December" without the year (decision 17). The month total's line reads "Spend cap: $5.00. Reached this month." or "Not reached.", with the amount formatted by the chat's `formatThreshold`.

### 27. Build note: where the chat shows the cap

`ChatError` shows `SpendCapAlert` after the provider-key and model alerts, for a `SpendCapReachedError`. The alert puts the message in its own element, before the "Go to usage settings" link. `fromStored` checks `error_code == "spend_cap_reached"` before its generic failed branch, so a stored answer that ended at the cap gets decision 10's text and `endedInTurn`, whatever its status. A stream `error` event with that code sets `endedInTurn` too; a `409` refusal before any turn does not, so its resend still takes the shortcut. Where an answer restarts (`retry()`, a replay), `endedInTurn` is cleared with the error. The compact dialog's failed step shows `SpendCapAlert` and, under it, "Nothing in the conversation changed." in place of the plain alert.

### 28. Build note: how the chat knows Stop can be pressed

`streamChat` and `followTurn` take an optional `onOpen` callback, called once the server has answered with the stream (a 2xx response, before its first event; not on a refusal or a follow's `204`). The chat keeps three states apart from `answering`: `chatTurn` (a chat turn is being sent or followed, so `/compact` and the held-proposal check never get `onStop`), `streamOpen` (set by `onOpen`), and `stopping`. `Composer` gets one more prop than decision 5 names, `canStop`: Stop shows in place of Send for the whole turn, and is disabled until `streamOpen` and the conversation id are both known, which for a new conversation means after its `conversation` event. Stop is a `type="button"`, so Enter in the input never presses it. A failed stop request sets `stopFailed` on the answer the chat is reading ("The answer could not be stopped. Try again.") and clears `stopping`; the next press and any terminal event clear it. A `401` from the stop request sends the user to log in, as other requests do. Each tool line carries `data-state`, so tests can see a stopped line is not running. The two existing tests that expected a disabled Send while an answer runs now expect Stop in its place, as decision 5 says.

## Risks / Trade-offs

- [Two conversations crossing the cap together] → Each turn checks before its next round, so the overshoot is at most one round per running conversation. Accepted: a strict cap would need a lock on every model call.
- [A provider keeps generating after the stream is closed and bills for it] → Not visible to us. The estimate counts only what arrived. Accepted and noted in the cap form's "estimated" wording.
- [Estimates under-count reasoning tokens] → Same as above; the stopped round's row is still closer than no row.
- [One more sum query per round when a cap is set] → It uses the `(user_id, created_at)` index and runs once per round, as the warning already does.
- [A stop races a terminal store or a commit along the way] → Decision 3: a cancel only reaches the model stream and a connector call's `provider.call()`, never a store. A stop that comes during a store takes effect at the next check, or not at all after the last one, so no row is counted twice and no stored card goes unshown.
- [A stop waits for the next check] → Between checks the turn makes database calls and, in a built-in tool, at most one embedding call with its 10-second timeout. It never fetches the model list (decision 4), so the wait is a few seconds at most. A stop after the final round's stream has ended does nothing, and the answer shows as complete (spec scenario "Stop as the answer finishes").
- [Shutdown while a turn is stopping] → Decision 1: the lifespan exit does not cancel it and waits within the same bound, so the stopped store and `run`'s `finally` never share the session at the same time. The stopped store makes only database calls and never fetches the model list (decision 4). A store that outlasts the bound is left to the start-up sweep of `background-turns`, which stores `failed` / `answer_interrupted` when no stopped answer was committed; conversation-agent "Conversations run independently" says so.
- [A stop during a connector call that wrote remotely] → Decision 12: the stored text says it may have run, so neither the model nor the user takes it as not done.
- [A delete while a message is being opened] → Decision 13: every delete claims the conversations it removes after `stop_turns`, so a message that holds a claim, in the registry or not yet, makes the delete answer 409 and delete nothing. The user tries again a moment later, when the answer is in the registry and the delete stops it. The one gap left is a first message of a new conversation committed between the delete's count and its delete statement, a few milliseconds in the same transaction: its turn may then fail on the foreign key. Accepted: it needs a new conversation sent in that instant, and a claim cannot cover a row that does not exist yet.
- [Deleting one's usage resets the month's sum] → The cap is the user's own limit, not the operator's. The confirmation and the cap form say so (decision 6).
- [An old frontend on the new backend] → It shows `spend_cap_reached` as a plain error with the backend's message, and has no Stop. Nothing breaks.

## Migration Plan

1. One Alembic migration adds `user_settings.cap_unit` and `user_settings.cap_amount`, both nullable. Existing users have no cap.
2. No data migration. `stopped` is a new value in a free text column, and `details.stopped` a new key in a JSON column.
3. Deploy the backend, then the frontend. Rollback: the previous image ignores the two columns; the downgrade drops them. A `stopped` message read by old code shows as a failed answer, which is harmless.

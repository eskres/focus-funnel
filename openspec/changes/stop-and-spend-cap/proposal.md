## Why

Users pay for every model call with their own keys, and today nothing lets them stop spending. An answer cannot be stopped once it starts (`background-turns` decision 5 left the Stop button out), and the monthly warning threshold in `usage-tracking` only shows a notice. A user who sees an answer going wrong, or who has a budget, needs a way to end the answer now and a limit the chat will not pass.

## What Changes

- A Stop button replaces Send while an answer is running. It ends the turn on the server, not only the browser's view of it. It works in every tab that shows the running answer, including a second tab that follows it. Only the owner can stop a turn; another user's conversation is 404.
- New endpoint `POST /api/chat/{conversation_id}/stop`, owner-scoped. It ends the running turn and answers `204` at once: the model stream or connector call in flight is cancelled, and a turn caught elsewhere (storing something, or in a search or proposal, which always finishes) ends before its next model or tool call; it also answers `204` when no turn is running or a stop is already under way. The chat waits for the stream's terminal event, as for any other end.
- A stopped answer keeps what it produced: the text so far, earlier rounds, tool results that finished, sources, and a proposal card already shown. It is stored with a new message status `stopped` and code `answer_stopped`, which is not an error. It is not `failed` / `answer_interrupted`, which stays the code for a server stop. A search or proposal that was running when Stop came finishes and is kept; a tool call that had not started is stored as not run, so the next message works. A connector tool that may already have reached its server is stored as stopped while it ran, saying it may have run, so the model does not repeat a write that happened. A tool whose call was still arriving from the model is not stored as a call; its name is kept on the stopped answer. The chat shows every such tool as "Stopped before it finished", live and after a reload. An action card already shown stays pending and can be approved.
- The stopped round's usage is recorded with the tokens the provider reported so far, or with estimated tokens when it reported none. An embedding call made before the stop keeps its usage record. The turn reads the model's prices once, when the call opens, so neither a stop nor its usage row waits on the provider's model list.
- Deleting a conversation, deleting content or the account, and ending or expiring a demo session first stop the user's running turns and wait for them, so no turn keeps spending a key after its data is gone and its last round's usage is kept. Each delete then claims the conversations it removes, so a message still being opened counts as running. When an answer has not ended in time, or a message is still being opened, the delete answers `409` `conversation_busy` and deletes nothing, with its own message ("An answer in this conversation is still running. Try deleting again in a moment." for a conversation, "An answer is still running. Try again in a moment." for content, account, and demo); an expired demo session is deleted on a later pass. A send refused as busy keeps today's message.
- A monthly spend cap in Settings (Usage section), in estimated dollars or in tokens, beside the existing warning threshold. Once the month's usage reaches it, new chat turns and `/compact` are refused with `409` and the new code `spend_cap_reached`. The chat shows the reason in place of the answer, and the summary dialog shows it for `/compact`, with a link to the usage settings. A refused chat message is kept, also the first message of a new conversation, whose id now reaches the browser; a refused `/compact` changes nothing.
- A turn that crosses the cap while it runs finishes the model call in flight and starts no further one. It ends with `spend_cap_reached`, keeping what it produced.
- Everything in `usage_events` counts toward the cap: chat, `/compact`, offers, tests, and embeddings, for the calendar month in UTC (the same month as the usage section's total). Calls with unknown cost add nothing to a dollar cap; a token cap counts their tokens.
- Embedding calls (search, saving, edits, additions, rebuilds), the model test in Settings, and approving or declining a connector action are not refused at the cap. A message refused at the cap, or refused for any other reason before its first model call is sent, does not expire pending action cards; a message whose first model call the provider refuses still expires them.
- The cap is read fresh at each check, so a cap set or lowered while a turn runs ends that turn before its next model call. The offer before archive asks no model at the cap, so archive still works.
- Deleting the usage history makes the cap count from zero again for the month; the confirmation says so, and so does the cap form outside demo mode (demo mode has no delete choice).
- New endpoint `PUT /api/usage/cap`; `GET /api/usage` gains `cap`. Demo mode works the same; a demo visitor's cap is deleted with the rest of their data.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `usage-tracking`: new requirements for the monthly spend cap: setting it, what counts, refusing new turns and `/compact`, ending a running turn at the cap, and what is not refused. Modified requirement "Every model call is recorded": a stopped round is recorded with the tokens reported so far, or estimated ones, and an embedding call made before a stop keeps its record.
- `conversation-agent`: new requirements: the owner can stop a running turn, a second stop does nothing more, a stopped turn stores what it produced, a stop stores each thing once, and a stopped turn and connector calls. New requirements: deleting stops the running turn first, and a delete is refused while an answer cannot be stopped in time. Modified requirement "Conversations run independently" (as changed by `background-turns`): the owner can now stop a turn, a delete or an ended or expired demo session also stops it, a stopped turn frees the conversation like any other end, and a server stop during a stop keeps it stopped. Modified requirement "The offer before an action may propose nothing" (as changed by `thought-appending`, then by `thought-status`): at the spend cap the model is not asked.
- `chat-interface`: new requirement: the Stop button, in every tab that shows the running answer. Modified requirement "Errors are shown in the chat": a message refused at the spend cap says so and names the cap, also in the `/compact` dialog; an answer that ended at the cap says the cap was reached; both link to the usage settings. Modified requirement "Sending a message": a stopped answer unlocks the input like a finished or failed one. Modified requirement "Thinking is shown": a stop ends the thinking indication. Modified requirement "Answers arrive a piece at a time" (as changed by `background-turns`): a stored stopped answer shows as stopped, not as cut short.
- `mcp-connectors`: modified requirement "A tool acts only after the user approves" (from `mcp-connectors`, stacked below): a message refused before its first model call is sent does not expire the conversation's actions, and one whose first model call the provider refuses or fails does.
- `account-data-deletion`: modified requirement "Deleting in settings": the usage history confirmation says that a spend cap, if one is set, counts from zero again. Modified requirements "Delete my content" and "Delete my account": running answers are stopped first, and the delete answers `409` `conversation_busy` and deletes nothing when one has not ended in time or a message is still being opened.
- `conversations`: modified requirement "A conversation can be deleted with /delete": its running answer is stopped first, and the delete answers `409` `conversation_busy`, with a message the confirmation shows, when the answer has not ended in time.

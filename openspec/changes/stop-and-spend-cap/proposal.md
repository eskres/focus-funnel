## Why

Users pay for every model call with their own keys, and today nothing lets them stop spending. An answer cannot be stopped once it starts (`background-turns` decision 5 left the Stop button out), and the monthly warning threshold in `usage-tracking` only shows a notice. A user who sees an answer going wrong, or who has a budget, needs a way to end the answer now and a limit the chat will not pass.

## What Changes

- A Stop button replaces Send while an answer is running. It ends the turn on the server, not only the browser's view of it. It works in every tab that shows the running answer, including a second tab that follows it. Only the owner can stop a turn; another user's conversation is 404.
- New endpoint `POST /api/chat/{conversation_id}/stop`, owner-scoped. It ends the running turn and answers `204` at once: the model stream or tool call in flight is cancelled, and a turn caught between them, while it stores something, ends before its next model or tool call; it also answers `204` when no turn is running or a stop is already under way. The chat waits for the stream's terminal event, as for any other end.
- A stopped answer keeps what it produced: the text so far, earlier rounds, tool results that finished, sources, and a proposal card already shown. It is stored with a new message status `stopped` and code `answer_stopped`, which is not an error. It is not `failed` / `answer_interrupted`, which stays the code for a server stop. A built-in tool that had not finished when Stop came is stored as not run, so the next message works. A connector tool that may already have reached its server is stored as stopped while it ran, saying it may have run, so the model does not repeat a write that happened. A tool whose call was still arriving from the model is not stored as a call; its name is kept on the stopped answer. The chat shows every such tool as "Stopped before it finished", live and after a reload. An action card already shown stays pending and can be approved.
- The stopped round's usage is recorded with the tokens the provider reported so far, or with estimated tokens when it reported none. An embedding call that answered before the stop keeps its usage record.
- A monthly spend cap in Settings (Usage section), in estimated dollars or in tokens, beside the existing warning threshold. Once the month's usage reaches it, new chat turns and `/compact` are refused with `409` and the new code `spend_cap_reached`. The chat shows the reason in place of the answer, and the summary dialog shows it for `/compact`, with a link to the usage settings. A refused chat message is kept, also the first message of a new conversation, whose id now reaches the browser; a refused `/compact` changes nothing.
- A turn that crosses the cap while it runs finishes the model call in flight and starts no further one. It ends with `spend_cap_reached`, keeping what it produced.
- Everything in `usage_events` counts toward the cap: chat, `/compact`, offers, tests, and embeddings, for the calendar month in UTC (the same month as the usage section's total). Calls with unknown cost add nothing to a dollar cap; a token cap counts their tokens.
- Embedding calls (search, saving, edits, additions, rebuilds), the model test in Settings, and approving or declining a connector action are not refused at the cap. A message refused at the cap does not expire pending action cards. The offer before archive asks no model at the cap, so archive still works.
- Deleting the usage history makes the cap count from zero again for the month; the confirmation says so, and so does the cap form outside demo mode (demo mode has no delete choice).
- New endpoint `PUT /api/usage/cap`; `GET /api/usage` gains `cap`. Demo mode works the same; a demo visitor's cap is deleted with the rest of their data.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `usage-tracking`: new requirements for the monthly spend cap: setting it, what counts, refusing new turns and `/compact`, ending a running turn at the cap, and what is not refused. Modified requirement "Every model call is recorded": a stopped round is recorded with the tokens reported so far, or estimated ones, and an embedding call made before a stop keeps its record.
- `conversation-agent`: new requirements: the owner can stop a running turn, a second stop does nothing more, a stopped turn stores what it produced, a stop stores each thing once, and a stopped turn and connector calls. Modified requirement "Conversations run independently" (as changed by `background-turns`): the owner can now stop a turn, and a stopped turn frees the conversation like any other end. Modified requirement "The offer before an action may propose nothing" (as changed by `thought-appending`): at the spend cap the model is not asked.
- `chat-interface`: new requirement: the Stop button, in every tab that shows the running answer. Modified requirement "Errors are shown in the chat": a reached spend cap says so and links to the usage settings, also in the `/compact` dialog. Modified requirement "Sending a message": a stopped answer unlocks the input like a finished or failed one. Modified requirement "Thinking is shown": a stop ends the thinking indication. Modified requirement "Answers arrive a piece at a time" (as changed by `background-turns`): a stored stopped answer shows as stopped, not as cut short.
- `account-data-deletion`: modified requirement "Deleting in settings": the usage history confirmation says that a spend cap, if one is set, counts from zero again.

## Impact

- Backend: `app/chat/running.py` (from `background-turns`: `stop()`, `shutdown()` so a turn's task is cancelled at most once, and the stop end of `run`), `app/main.py` (the `background-turns` lifespan exit goes through `shutdown()` and waits without cancelling again), `app/chat/turn.py` (the `interruptible` and `stop_requested` flags, set only around the model stream and `provider.call()`, the stop check before each of them, the stopped store, not-run and may-have-run tool messages, embedding usage rows kept through the rollback, the reported or estimated usage row, the cap check between rounds, the tool message with its proposal or `tool_actions` row committed before the `proposal` or `action` event, the names of tools cut off mid-call on the stopped answer, provider `aclose()` shielded in the turn's own `finally`), `app/chat/tool_providers.py` (from `mcp-connectors`: whether a connector call may reach its server), `app/chat/usage.py` (`cap_state()`), `app/routers/chat.py` (stop route, cap check before a turn and before `/compact`, the `mcp-connectors` action expiry moved after the cap check and committed on its own before `turn.open()`), `app/chat/proposal.py` (no model call at the cap), `app/routers/usage.py` (`cap` in the report, `PUT /api/usage/cap`, which creates the `user_settings` row when it is missing), `app/errors.py` (`spend_cap_reached`, `answer_stopped`), `app/models/chat_settings.py` and one Alembic migration (two nullable columns on `user_settings`).
- Frontend: `app/api/[...path]/route.ts` (`x-conversation-id` added to the response headers the proxy passes back), `lib/chat.ts` (`stopTurn`), `lib/usage.ts` (`cap`, `saveCap`), `lib/api.ts` (two error classes), `components/chat/composer.tsx` (Stop button), `components/chat/chat.tsx` (stop, the stopped state, stopped tools, `fromStored`, no resend shortcut after a stopped answer or one that ended at the cap during its turn, the error code kept in `runCompact`), `components/chat/message-list.tsx` (stopped note, stopped tool label), `components/chat/compact-dialog.tsx` (the cap alert in the failed step), `components/delete-data-settings.tsx` (one fixed cap sentence in the usage history confirmation), `components/chat/chat-error.tsx` and a new `components/chat/spend-cap-alert.tsx`, `components/usage-settings.tsx` (cap form and state, the usage-history sentence left out in demo mode).
- API: new `POST /api/chat/{conversation_id}/stop` and `PUT /api/usage/cap`; `cap` on `GET /api/usage`; message status `stopped`; tool messages of a stopped turn carry `details.stopped`, and a stopped answer may carry `details.stopped_tools`. No breaking change.
- Depends on `background-turns` (planned, not yet built on this branch): the Stop work needs its registry and its cancel path. The cap work does not. Builds on `mcp-connectors` (tool providers, connector calls, action cards, action expiry) and `thought-appending` (the offer's text), both stacked below.

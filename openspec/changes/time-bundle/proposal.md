## Why

`thought-dates` gave a thought a date, and left three things out on purpose (its design, Non-Goals): reminders, repeating dates, and a calendar export. A dated task that nobody is reminded of is easy to miss. "Take the bins out every Monday" can only be filed as one Monday. And a user who lives in their phone's calendar cannot see their dated thoughts there. The stored time zone was kept so these could come later. This change adds all three, sized for a self-hoster: no new service, one backend process, Postgres as the only store.

## What Changes

- **A small job runner in the backend process.** One asyncio loop, started and stopped in the lifespan beside `background-turns`' running turns. Each job has a name and an interval. When each job is next due is kept in Postgres, so a restart does not lose a run, never runs a job twice at the same time, and a job that must not repeat its effect (reminders) makes its writes idempotent. A job missed during downtime runs once at start. Reminders are its first job; feature 7 (weekly review, resurfacing) adds its own jobs to the same runner. It always runs, in every auth mode; there is no operator switch to turn it off, so a reminder set in the app always fires.
- **Repeating dates.** A dated thought can repeat: every N days, weeks (on one or more weekdays), months (on the start's day of the month), or years, with an optional last day. The `when` shape gains `repeat`, for example `{"every": "week", "interval": 1, "weekdays": ["mon"], "until": null}`. The start is the first occurrence. A repeating date's end, when it has one, is on its start day.
  - The model proposes a repeat only when the user says the thing repeats ("every Monday", "each month on the 1st"). The card and the sheet show the repeat, and the user can change or clear it.
  - The Upcoming page lists a repeating thought once, at its next occurrence. A search by the thought's date finds a repeating thought when one of its occurrences falls in the days asked for, and shows that occurrence.
  - Status stays one value per thought. Marking a repeating thought done ends the series. The model does not mark a repeating thought done because one occurrence happened, and the status card says the thought stops repeating.
- **Reminders.** A dated thought can have up to five reminders, each a number of minutes before its start (0 for "at the time"). A day with no time counts as starting at 09:00 in the thought's zone. A repeating thought reminds before each occurrence. The model adds a reminder only when the user asks to be reminded; the card and the sheet set, change, or remove them.
  - A due reminder becomes an in-app notification: a "Notifications" link in the sidebar with an unread count, and a page listing them, each opening its thought.
  - Delivery is once: a restart in the middle of a run does not send a reminder twice. After downtime, each reminder sends at most its latest missed occurrence, and only when it is at most 24 hours late.
  - A done or deleted thought sends no more reminders.
- **Web push, only when the operator turns it on.** With `WEB_PUSH_VAPID_PUBLIC_KEY` and `WEB_PUSH_VAPID_PRIVATE_KEY` set (off by default, refused in demo mode, and left off in the offline install, since push services are on the internet), Settings offers "Browser notifications". The browser's push subscription is stored per user, with the key it was made under, and never returned or logged. A reminder then also shows as a browser notification. Push goes only to known push services. A browser gets pushes for one user at a time, the last one who turned them on there; opening a page never takes another account's subscription, and signing out turns them off in that browser. The app restores a subscription the browser renewed when it next loads. New VAPID keys turn push off in every browser until each user turns it on again. No other channel is added: SMTP stays out.
- **A calendar feed.** In Settings, a user can make a private feed address, `/api/calendar/<token>.ics`, to subscribe to in a calendar app. The token is random, shown once, and stored only as a hash. "Regenerate" replaces it, and "Turn off" revokes it; the old address stops working at once.
  - The feed holds the user's open dated thoughts, with repeats as repeat rules: title, summary, and category, and nothing else. No reminders, tags, raw text, or account details.
  - The feed request needs no login: the token is its credential. The Next.js server forwards only that path to the backend, without a session. Requests are rate-limited, the token never reaches the access log, and an unknown or revoked token gets the same 404 as any unknown address.
  - Demo mode offers no feed.
- **The email allow-list still applies.** A user the operator removes from `AUTH_ALLOWED_EMAILS` gets no feed and no push, though neither needs a login: each keeps the verified address it was set up with, checked against the list.
- Deleting content deletes reminders and notifications. Deleting the account also deletes the feed and push subscriptions. The delete confirmations say so.

## Capabilities

### New Capabilities

- `scheduled-jobs`: the in-process job runner: when a job runs, what is kept in Postgres, catching up after downtime, failures, and shutdown.
- `reminders`: reminder times on dated thoughts, when a reminder is due, delivering it once, catching up after downtime, and reminders stopping for done and deleted thoughts.
- `notifications`: the in-app notification list and unread count, how long notifications are kept, and the optional web push channel with its subscriptions.
- `calendar-feed`: the private feed address, its token, what the feed holds, rate limits, revoking it in Settings, and demo mode.

### Modified Capabilities

- `thought-store`: new requirements: a dated thought can repeat, and can have reminders; both are checked.
- `thought-filing`: new requirement: a proposal can carry a repeat and reminders, which the card shows and the user can change before confirming.
- `conversation-agent`: modified requirement "The tools carry dates" (added by `thought-dates`): a repeating date starts at its first occurrence, today counting, with no choices; that delta is built on `thought-dates`' version. Modified requirements "The model proposes marking thoughts done", "The model finds a finished task it has not seen", "A finished task among similar thoughts is marked done", "The repeated-task line leaves room for a finished task", "A held part the user finished is not filed", "Several open matches mark the newest", and "A finished task with a held proposal" (added by `thought-status`): a repeating thought is marked done only when the user says it has ended or they stopped it, never for one occurrence, also under `/push`, among several matches, or beside a held proposal, and a held repeating part is kept; those deltas are built on `thought-status`' versions. New requirements: the model proposes reminders only when asked; the search result, the seen-thoughts note, the candidate lists, and the held-proposal note show the repeat.
- `thought-search`: modified requirement "Filters and order": a repeating thought passes the thought-date filter by its occurrences, and is ordered by its first occurrence in the days asked for. The delta is built on `thought-status`' version.
- `upcoming-thoughts` (added by `thought-dates`): modified requirement "The Upcoming page lists dated thoughts from today on": a repeating thought is listed once, at its next occurrence. The delta is built on `thought-status`' version of the requirement. Modified requirement "The Upcoming page groups by day": only a thought that does not repeat and started before today goes under "Today"; a repeating thought goes under its next occurrence's day. That delta is built on `thought-dates`' version.
- `thought-export` (added by `thought-export`): modified requirements "A user can export all their thoughts": each thought also carries its repeat and its reminders; and "The Markdown export": a section's date line shows the repeat, and a reminders line follows it.
- `offline-install` (added by `self-hosting-setup`): modified requirement "No runtime calls to the internet": web push off (no VAPID keys) is one more of its conditions, since push calls the browsers' push services.
- `thought-detail-view`: new requirement: the sheet shows and edits the repeat and the reminders.
- `chat-interface`: new requirement: a status card for a repeating thought says that marking it done stops it repeating.
- `account-data-deletion`: new requirement: reminders and notifications go with the content; the feed and push subscriptions go with the account; the confirmations say so.
- `auth-modes` (added by `auth-modes`): modified requirement "Email allow-list": a calendar feed request of a user the list does not let in answers 404 `not_found` with the unknown-address body, not 403 `not_allowed`, and such a user gets no pushes. The delta is built on `auth-modes`' version.
- `user-auth`: modified requirement "Backend API requires a valid access token": the calendar feed request is an exception, with its own token, and still follows the email allow-list. Modified requirement "Browser never holds the access token": the feed route of the app's server forwards with no credential or cookie, and answers without a session. Both deltas are built on `auth-modes`' versions.

New dependencies: `python-dateutil` (repeat rules), `icalendar` (the feed), `pywebpush` (push).
- Frontend: `components/chat/date-fields.tsx` (repeat and reminder fields, used by the card and the sheet), `components/chat/proposal-card.tsx`, `components/chat/thought-sheet.tsx`, `components/upcoming/upcoming-list.tsx`, `components/chat/sidebar.tsx` (Notifications link and count), a new `app/app/notifications/page.tsx`, Settings sections for notifications and the calendar feed, `lib/push.ts` and `components/notifications/push-restore.tsx` in `app/app/layout.tsx` (the restore on load), `public/sw.js` (`push` and `notificationclick` added to quick-capture's worker when it has landed, else a new file), a new `app/api/calendar/[file]/route.ts`, `proxy.ts` (`/sw.js` loads without a session, keeping quick-capture's rule when it is in place), `lib/account.ts` (`signOut()`, which unsubscribes this browser) and every sign-out link, and the confirmations in `components/delete-data-settings.tsx`.

- Deployment: still one backend process (`background-turns`). The runner fits that: it is one more task in the same process. A second process started by mistake would still send no reminder twice (the job claim and each notification's unique key), but `background-turns` already rules it out.

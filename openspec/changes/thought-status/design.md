## Context

See `proposal.md` for why. This change sits on top of other changes, and plans against their specs and design.

Built on this branch:

- `thought-editing`: `PATCH /api/thoughts/{id}` with a closed field list (`ThoughtPatch`, `extra="forbid"`), `update_thought()` that re-indexes only what changed, `saved_title` and `deleted` on proposal parts (one query in `saved_titles()`, filtered by `Thought.user_id`), the `ff:thought-changed` window event, and Edit and Delete in `ThoughtSheet`.
- `event-category`: `event` is the sixth fixed kind. The Alembic head is `4d7a1c9e2b60` (`self-hosting-setup`).

Planned, not built here, and treated as in place:

- `thought-dates`: the `when` date columns, `dated_from`/`dated_to` on the search tool, a search with no query when a date range is given (a plain select in date order, no embedding call), and the Upcoming page with `GET /api/thoughts/upcoming`. It adds the `upcoming-thoughts` capability, and modifies `thought-search` "Filters and order".
- `thought-appending`: refs (`T1`, `T2`, …) for every thought a conversation has seen, the seen-thoughts note on every turn, `add_to` parts resolved from a ref in `write_proposal()`, `target` on proposal parts (the thought's current fields, read in the `saved_titles()` query), the similar-thought check (layers 1 to 3, also in the offer), the `based_on` and `after_updated_at` checks against `updated_at`, and `mode` on confirm. A bad `add_to` ref becomes a new thought; a tool argument error goes back to the model for another round.
- `background-turns`: no overlap with this change (Risks).
- `mcp-connectors`: moves `_run_tool()`'s search and propose code into `BuiltinTools`, which returns a `ToolOutcome`, and keeps one shared error handler in `_run_tool()`. This change edits the same propose branch and the same error handling (Risks). It also adds its own `connectors.tool_rounds` (5) for conversations with a connector on.

What exists on this branch, and matters here:

- `thoughts` has no status. `updated_at` has `onupdate=func.now()`, so any ORM update of the row moves it. The sheet shows it as the "changed" date.
- `parse_proposal()` in `app/chat/tools.py` reads each entry of `thoughts` as title, summary, tags, and category, and refuses an entry with no title or summary as a `ToolArgumentError`. The tool schema requires all four, and `thoughts` has `minItems: 1`. A call with no `thoughts` is refused, unless it has a top-level `title` (an older call shape, read as one part).
- `Turn._run_tool()` in `app/chat/turn.py` sends every `ToolArgumentError` back as `Error: <message>. Call the tool again with valid arguments.`, with the chat summary `The tool call was not valid`. After a written proposal, the tool result is `PROPOSAL_SHOWN`, which calls the card editable and lists the words the reply must avoid (saved, noted, added, recorded), and the summary is `Proposed a thought to file`. A search's summary is `Searched your thoughts for “<query>”`. The summary goes only into the live `tool` end event: the stored tool message's `details` hold only `sources` or `proposal_id`, and on reload `fromStored()` in `chat.tsx` builds each tool line from the call's name alone, with `doneLabels` in `message-list.tsx` (`Searched your thoughts`, `Proposed a thought to file`).
- `HELD_PROPOSAL_NOTE` says that when the latest message is about something else, the model's first action must be a `propose_thought` call with the held proposal. A second `propose_thought` in a turn gets `ALREADY_PROPOSED` and stores nothing ("One proposal per answer").
- `ProposalGroup` in `proposal-card.tsx` decides on load that a proposal was merged when it has two or more parts and every part has the same non-null `thought_id`, and then shows one card built by `mergeParts()`. Its region is named `Proposal to file` or `Proposals to file`.
- In the propose branch, `_run_tool()` calls `drop_held_note()` and clears `self.held_parts` before `write_proposal()`. Only `parse_proposal()`, which runs before them, can refuse a call today. `drop_held_note()` finds the note by rendering `held_proposal_note()` again and comparing the text.
- `Turn.events()` makes at most `chat.yaml` `tool_rounds` (3) model calls. The reply after the last tool call needs a call of its own, so a turn has at most two rounds of tool calls before it answers; a third ends in `tool_loop_limit`.
- A part counts as saved when it has a `thought_id`. `prompt.py` (`unsaved_parts()`, the held note), `proposal.py` (`held_parts()`, `discussion_start()`, `filed_titles()`, the offer, and the replace test in `write_proposal()`), and confirm all rely on it. `write_proposal()` always makes the new proposal the held one, and marks the earlier held proposal replaced when it still has an unsaved part. The chat folds a replaced proposal's unsaved cards away, and the offer dialog (`proposal-dialog.tsx`) shows a held proposal's cards with `thought_id === null`. `discussion_start()` sets where the raw text of a later proposal starts, and whether the offer before archive and `/compact` asks the model at all.
- The offer (`offer_proposal()`) makes one asked call and passes its parts to `write_proposal()`. `asked_proposal()` catches only parse errors, logs a fixed line with no user content, and then returns None, so nothing at all is offered; there is no round to correct a call. `thought-appending` decision 4 adds a second asked call when layer 1 finds candidates for the first call's new parts, with the candidate note appended; it goes through `asked_proposal()` the same way. So the offer can make two asked calls, and neither can be corrected.
- Confirm (`POST .../proposals/{id}/confirm`) locks the proposal row, answers a repeated confirm with the saved `thought_id` and the message `Saved.` before anything else, and clears the held proposal once every part is saved.

## Goals / Non-Goals

**Goals:**

- One status field, set the same way from a confirmed card and from the sheet.
- A status change costs no embedding call and changes nothing else about the thought.
- No new tool, no new proposal kind outside `proposals.parts`, no change to the new-thought part schema, and no change to the one-proposal-per-answer rule.
- The later features (library, export, weekly review, resurfacing) read status from one column with no further migration for open and done.

**Non-Goals:**

- `archived` as a status, and any archive action (decision 2).
- Reopening from the chat. The sheet's toggle reopens. A later change can add it as a field on a stored status part with no migration, because parts are JSON.
- The thoughts library page, export, the weekly review, and resurfacing of untouched ideas. They build on this status later.
- Filing a new thought as done. A new thought is always open.
- Marking a thought done from its date passing, from an addition, or in bulk.
- A history of status changes. Only the last change's time is kept.
- Showing the status in the sources list under an answer. It stays the record of what the answer read (`thought-editing` decision 5).
- Leaving done thoughts out of the similar-thought check. A done task is still a candidate; `thought-appending` already tells the model a repeated task is usually new, and the candidate list marks a done candidate done (decision 12).
- An undo on a confirmed status card. The sheet's toggle sets it back.

## Decisions

### 1. Every thought has a status: `open` or `done`

A status belongs to every thought, not only to `task`. A new thought is `open`; existing thoughts become `open` in the migration.

Categories are the user's own and can change: a user may add `errand` or `chore`, or change a task to a note. A status tied to `task` would vanish or need rules each time. The library filter and export later read status from every thought. Most ideas and notes simply stay `open`, which costs nothing.

**Alternatives:** status only on `task` thoughts, null on others (rejected: a category edit would have to create or drop the status, and added task-like categories would get none); a boolean `done` (rejected: decision 2 needs a third value later).

### 2. `archived` is not a status in this change; a later change adds it to the same column

Feature 7 (resurfacing untouched ideas with keep, archive, or delete) needs "archive". It is out of scope here. When it is built, it adds `archived` as a third value of `thoughts.status`, with its own migration that widens the check constraint, and its own UI. It needs no new column: `status_changed_at` (decision 3) already says when the thought was archived.

So that this costs nothing later, every "open" list in this change asks for `status = 'open'` by name, never `status != 'done'`. An archived thought then drops out of the open search filter and the Upcoming page with no change. A search with no status filter will still find archived thoughts, as it finds done ones.

The text the model reads and the mark check key on "not open" in the same way, never on `done`: the status marker (decision 12) prints ` · <status> <date>` for any status other than `open`, and a mark on a thought whose status is not `open` is refused with `Error: T9 is already <status>. …` (decision 6). Today both read `done`, so the output and the texts are the ones the specs name. Written the other way round, an archived thought would look open to the model, and a mark on it would pass the check and set it to done. So feature 7 changes neither.

**Alternatives:**

- Add `archived` now, with no way to set it (rejected: a value no request can set and no spec scenario can test is scope creep).
- A separate `archived_at` column, now or later (rejected: two columns for one state, and every open list would have to check both; a thought could be done and archived at once, which no feature asks for).
- Delete instead of archive (rejected for feature 7: the user asked for archive and delete as two choices).

### 3. Two columns, and a status change keeps `updated_at`

`thoughts` gains:

- `status TEXT NOT NULL DEFAULT 'open'`, with a check constraint `status IN ('open', 'done')`. The model declares it as `CheckConstraint("status IN ('open', 'done')", name="status")` in `Thought.__table_args__`; the metadata naming convention (`ck_%(table_name)s_%(constraint_name)s` in `app/db.py`) makes it `ck_thoughts_status`. The migration names it `op.f('ck_thoughts_status')`, as `setup_state` does, and adds it inside `op.batch_alter_table("thoughts")`, so SQLite (where `env.py` already turns on batch mode) rebuilds the table. Naming it `ck_thoughts_status` in the model would render as `ck_thoughts_ck_thoughts_status`.
- `status_changed_at TIMESTAMPTZ NULL`: the time of the last change of status, null while it never changed.

A status change does not move `updated_at`. Three reasons:

- The sheet's "changed" date is the date the content changed. A done date is shown on its own (decision 13).
- `thought-appending` compares `updated_at` with the part's `based_on` before an addition, and with `after_updated_at` before an undo. If marking a task done moved `updated_at`, an addition proposed before it would get a 409 for a field it does not touch, and the last addition could no longer be undone. Those two `thought-appending` requirements say a confirm or an undo is refused when "the thought changed", so the `thought-filing` delta adds "A status change does not block an addition": a status change does not count there. An undo restores the addition's `before` (title, summary, tags, category, raw text), which holds no status, so it keeps the status and `status_changed_at`; an addition's confirm writes no status either.
- Feature 7's "untouched" can read content changes from `updated_at` and status changes from `status_changed_at`, and decide which count.

The mechanism is a Core `UPDATE` that sets `updated_at` to the column itself (decision 4, step 4). When a statement gives a value for `updated_at`, SQLAlchemy does not add the column's `onupdate`, and a column expression keeps the stored value as it is. Setting the attribute to its own value on the ORM instance does not work: tested on the backend's SQLAlchemy, an unchanged value is dropped from the `SET` clause, and the statement becomes `UPDATE thoughts SET status=?, updated_at=CURRENT_TIMESTAMP`.

**Alternatives:** let `updated_at` move (rejected: the two `thought-appending` checks above); a constraint with no name (rejected: the convention needs `constraint_name`, and `alembic check` would compare an unnamed constraint); `flag_modified(thought, "updated_at")` on the ORM path (rejected: it writes back the value Python holds, so it depends on that value being loaded and round-tripping exactly, while the Core statement never leaves the database); `done_at` only, with the status read from it (rejected: decision 2's `archived` would need another column, and every filter becomes a null test); a status history table (rejected: no feature reads the history).

### 4. One store function, used by confirm and by `PATCH`

`set_status(session, user, thought_id, status)` in `app/thoughts/store.py`:

1. Loads the thought with `get_thought()`, so another user's thought and a missing one raise `not_found` with the same body.
2. Refuses any value but `open` or `done` with `validation_error` and the message `status: must be open or done`.
3. Returns the thought unchanged when the status is the same.
4. Otherwise runs `update(Thought).where(Thought.id == thought.id, Thought.user_id == user.id, Thought.status != status).values(status=status, status_changed_at=func.now(), updated_at=Thought.updated_at)` and reads the row count. With one row, it refreshes the instance, so the caller reads the new status and change time and the old `updated_at` (decision 3). With none, another request changed or deleted the thought after step 1: it reads the thought again with `get_thought()` (with `populate_existing`), so a deleted one raises the usual `not_found`, and one that already has the status is returned unchanged. It does not commit, so confirm can commit it with the part's `thought_id`, as `add_thought()` does.

The `status != status` guard keeps "the same status changes nothing" true when two requests race: a confirm from two conversations, or a confirm and a sheet `PATCH` (confirm locks the proposal row, not the thought). Both pass step 3, but only the first `UPDATE` matches, so `status_changed_at` keeps the first write's time. Without the re-read, a thought deleted between step 1 and step 4 would make the refresh raise instead of answering 404.

It touches no search entry and makes no provider call. Status is not in `search_tsv` or in any embedded piece, so nothing in search needs to change.

`ThoughtPatch` gains `status`. The route calls `set_status()` first when `status` is in the body, then `update_thought()` for the other fields when there are any. `update_thought()` commits both; with `status` alone, the route commits. A refused field after the status rolls the status back with it, since the session closes without a commit. `GET` and `PATCH` answer `status` and `status_changed_at`. The status path is a new place that answers 404, so it gets its own check that another user's thought gives the same body as an unknown id.

**Alternatives:** a separate `POST /api/thoughts/{id}/done` (rejected: `PATCH` already owns changes to a thought, its errors, and the proxy test); a `status` argument on `update_thought()` (rejected: its every path commits and moves `updated_at`, and confirm needs a write it commits itself); `SELECT … FOR UPDATE` on the thought in step 1 (rejected: SQLite ignores it, and the guarded `UPDATE` gives the same answer with no lock on either store).

### 5. Status changes as `marks` on `propose_thought`

`propose_thought` gains an optional array beside `thoughts`: `marks`, each entry `{"ref": "T3"}`, a thought the conversation has seen that the user finished. A mark always means "mark done"; there is no status field (Non-Goals). The new-thought part schema is left exactly as it is, with all four fields required. `thoughts` stays required in the schema but loses `minItems: 1`, so a call that only marks a task done sends `"thoughts": []`. Many providers do not enforce `required`, and a model marking one task done will often send only `{"marks": [{"ref": "T3"}]}`, so `parse_proposal()` reads a missing `thoughts` as `[]` when `marks` is present (the older top-level `title` shape is read as today). `parse_proposal()` reads `marks` on its own. It keeps one entry per ref: a mark carries only a ref and always means "mark done", and each thought has one ref, so a second mark with the same ref holds the same data and is dropped, not refused. It refuses:

- a call with no entry in `thoughts` and none in `marks`: `propose_thought needs at least one entry in thoughts or marks`;
- more than `MAX_PARTS` entries in both together;
- a mark with no `ref` string, naming `marks[0].ref`;
- a mark that also carries `add_to`, `new`, `summary`, or `thought-dates`' `when` or `when_choices`: `marks[0]: a mark only names a ref; send an addition as its own entry in thoughts`. So "I called the plumber, he comes Tuesday" cannot lose the addition or the date without a word. `thought-dates` adds `when` and `when_choices` to every part, and a model that marks the task done will more often put the date on the mark (`{"ref": "T1", "when": {"start": "2026-11-10"}}`) than write a summary; a date dropped there would be lost the same way. The message names an entry in `thoughts`, which is where a date goes.

These checks are for a turn. In the offer's asked call, `parse_proposal(..., offered=True)` ignores the `marks` key, whatever its shape: no mark check runs, marks do not count toward `MAX_PARTS`, and a call with no entry in `thoughts` makes no proposal, so nothing is offered (decision 6).

One answer still shows one proposal. "I called the plumber, and I need to buy oat milk" is one call with one entry in `thoughts` and one in `marks`, written as one proposal with two parts. `write_proposal()` resolves each mark with the refs from `thought-appending` and stores it in `proposals.parts`, after the new and addition parts:

```
{"mark": "<thought id>", "title": "<the thought's title now>", "summary": "",
 "tags": [], "category": "<the thought's category now>", "thought_id": null}
```

The stored title and category come from the thought. They are for the card only: they name the thought on the card if it is later deleted (decision 10). No log line holds a thought's title, category, or summary, as no log line in `app/chat/proposal.py` holds user content today. So the one-proposal-per-answer rule, confirm, and the card group handle a status part as one more part. The held proposal, the held note, the fold of replaced cards, and the offer leave it out (decision 9). A mark needs no new ref rule: it can only name a thought the conversation has already seen.

**The similar-thought check leaves marks out.** `thought-appending`'s layers 1 to 3 run on the call's new entries in `thoughts` only. A mark is not embedded and is never given `similar`, and the thought it names is excluded from the candidates of the other parts, as `thought-appending` excludes a thought named by `add_to`. A call with only marks makes no embedding call and has no candidate round. Without this, a mark would read as a new part (no `add_to`, no `new`), its best candidate would be the marked thought itself, and the card would be withheld for a candidate round.

**Marks are checked before layer 1, and survive a candidate round.** The mark checks of decision 6 run first, before layer 1 and any embedding call, so a bad mark costs one round and no provider call. A call with a mark and a new part that has candidates writes nothing, as `thought-appending` decision 4 says for any call. Its tool result asks only about the new parts, so a model often resends only `thoughts`, and the one-proposal-per-turn rule would then block the mark for the rest of the turn. So when the call had marks, the candidate round's tool result adds the line `Send the marks again in the same call.` The second call is checked for marks again (one query, no embedding).

**The tool result after a proposal with a status part.** `PROPOSAL_SHOWN` calls the card editable and forbids "saved, noted, added, or recorded", but not "marked done". When the written proposal has a part with `mark`, the turn sends `PROPOSAL_SHOWN_STATUS` instead: the proposal is shown as cards for the user to confirm; nothing changes until they confirm, so do not say a task is marked done, done, closed, or finished, or that anything is saved; say the change is ready for them to confirm. The rest is as in `PROPOSAL_SHOWN`.

**The chat summary.** When every part of the written proposal has `mark`, the tool event's summary is `Proposed marking a thought done`, not `Proposed a thought to file`. A proposal with any new part or addition keeps `Proposed a thought to file`.

**The chat summary is stored.** Today a reload rebuilds each tool line from the call's name, so `Proposed marking a thought done` and `Could not propose that change` (decision 6) would both come back as `Proposed a thought to file`, and `Listed your open thoughts in task` (decision 12) as `Searched your thoughts`: after a reload, a refused mark would claim something was proposed. So `_run_tool()` stores the summary on every tool message as `details.summary`, beside `sources` or `proposal_id`, and `fromStored()` sets the summary of the tool line whose call id matches the tool message's `tool_call_id`. A row with no `details.summary`, stored before this change, keeps the `doneLabels` text.

**Alternatives:**

- A status part inside `thoughts`, with `mark` and `status` on the part and only `title` required (rejected: it loosens the schema every new thought uses, which risks a model leaving out summaries; it asks the model to copy a title the server then replaces; and a part could carry `mark` together with `add_to`, which needs rules of its own).
- A third tool, `propose_status` (rejected: a turn that marks one task done and files a new one would show two proposals, against "One proposal per answer"; and every place that handles a proposal would need a second kind).
- A `status` field on an addition part (rejected: an addition always rewrites the summary and extends the raw text, which "I called the plumber" should not).
- Refuse two marks with the same ref, as `thought-appending` refuses a duplicate `add_to` (rejected: two additions carry different text, so one would be lost; two marks carry the same data, so a refusal only costs a round).
- Keep a candidate round's marks on the server for the next call (rejected: hidden state between two tool calls, which a model that changes its mind would not see; one line in the tool result does the same).
- The server marks a task done when the model's text says so (rejected: nothing changes without a confirmed card).
- Marks that can also reopen (rejected: the feature asks for marking done; the sheet's toggle reopens).
- Rebuild a reloaded tool line's summary in the browser from the stored call arguments and result text (rejected: the browser would have to repeat the server's wording rules, and a refusal can only be told from a proposal by parsing the result text; one stored string is the same on both paths).
- Drop a date sent on a mark, or keep it on the status part (rejected: dropped, the user's date is lost with no word to anyone; kept, a status part would change the thought's date on confirm, against decision 3, and the card would need date fields).
- Run the mark checks in the offer too, as in a turn (rejected: `asked_proposal()` gives up on any refused call, so one badly shaped mark would drop a valid new thought from the offer, and the discussion would be lost at archive).

### 6. A mark that cannot apply

`write_proposal()` checks every mark of the call, before layer 1 and any embedding call (decision 5), with one query for all of them: `select(Thought.id, Thought.status).where(Thought.id.in_(ids), Thought.user_id == user.id)`, with the ids the refs resolve to. This is the owner filter decision 10 uses for `target`. A thought of another user then reads as missing before any status is looked at, and gets the same "no longer exists" line as a deleted one, so the tool result never shows whether another user's thought is done. In a turn, a mark that cannot apply refuses the whole call. Nothing is stored, the call does not count as the turn's proposal, and the model gets another round. The tool result has one line for each mark that cannot apply, in the order of the call, not only the first, so two bad marks cost one round and not two. The lines, exactly:

- `mark` is not a ref the conversation has seen: `Error: T9 is not a thought this conversation has seen. Search for it with status open, then call propose_thought with the ref the search gives.`
- the thought no longer exists, or belongs to another user: `Error: T9 no longer exists. Do not propose marking it done; tell the user it was deleted.`
- the thought's status is not `open` (decision 2): `Error: T9 is already <status>. Do not propose marking it done; tell the user it is already <status>.` Today the only such status is `done`, so the line is `Error: T9 is already done. Do not propose marking it done; tell the user it is already done.`

When the refused call also had entries in `thoughts`, or marks that passed, the result ends with one more line: `Nothing was proposed. Call propose_thought again with the call's other parts, without T9.`, naming every refused ref (`without T9 and T12`). When a refused mark was not seen, the line ends `…, without T9, and with the ref the search gives, in one call.` instead. Without it, "I called the plumber, and I need to buy oat milk" with the plumber task already done throws the oat milk part away with a text that only speaks of the mark: a model that reads "Do not propose it" as the whole proposal only replies, and one that resends only the found mark is then blocked from proposing the oat milk by the one-proposal-per-turn rule. "Do not propose marking it done" names the mark, not the proposal. This is the same gap decision 5 closes for a candidate round with `Send the marks again in the same call.`

These raise `ToolRefusal`, a subclass of `ToolArgumentError` whose message `_run_tool()` passes through as it is, without the generic `. Call the tool again with valid arguments.` suffix. That suffix would push the model to propose again after "already done", when it should tell the user. Parse errors (decision 5) keep the suffix. The chat summary of a `ToolRefusal` is `Could not propose that change`, not `The tool call was not valid`: an "already done" refusal answers a correct call.

**The held note is dropped only after a written proposal.** Today `_run_tool()` drops the held-proposal note and clears `self.held_parts` before `write_proposal()`, which was safe while only `parse_proposal()`, earlier, could refuse. A `ToolRefusal` is raised inside `write_proposal()`. If the note were already gone, a refused call would leave the model without it: a user with a held oat-milk proposal says "I called the plumber, and I need to book the dentist"; on the change of topic the model re-proposes the oat-milk part, the dentist part, and a guessed mark, and is refused; with no note in front of it, its corrected call holds only the dentist part and the mark, replaces the held proposal, and folds the oat-milk card away. So `_run_tool()` drops the note and clears `self.held_parts` only when `write_proposal()` wrote a proposal row. On a `ToolRefusal`, the note stays in the context and the held proposal stays held. A candidate round from `thought-appending`'s layer 2 also returns normally but writes no proposal row; it keeps the note and `self.held_parts` too, so the model's next call still sees the held parts and does not replace the held proposal without them.

`drop_held_note()` today finds the note by rendering `held_proposal_note()` again and comparing the text. The note now depends on more than the parts (refs from `thought-appending`, dates from `thought-dates`, and which parts count as unsaved, decision 9), so a second render can differ and leave the note in place. So the `Turn` keeps a reference to the note dict that `build_context()` appended (`self.held_note`, the last context entry when the turn starts with held parts), and `drop_held_note()` removes that object by identity, with no second render.

This differs from `thought-appending`, where a bad `add_to` falls back to a new thought: a mark has nothing to fall back to.

**A refused call does not count for layer 2's skip.** `thought-appending` skips layer 2 on a second `propose_thought` in a turn, because the first one already asked the model about its candidates. A call refused with `ToolRefusal`, or with a parse error, wrote nothing, reached no layer, and asked nothing, so it does not count, just as a candidate round does not set `Turn._proposed`: the skip is keyed on a candidate round earlier in the turn, not on any earlier `propose_thought` call. The corrected call after a guessed ref then runs layers 1 to 3 in full. If the refused call counted, a new oat milk part would be filed with no similar-thought check only because the model guessed a ref. The cost is one flow that can need five calls (decision 11). This changes `thought-appending`'s rule, which its spec states as "a second proposal in the same turn SHALL be shown without another check", so this change modifies "Tools to file and find thoughts" to say that a proposal made after a candidate round skips the check, and that a refused call does not count (decision 15).

**In the offer before archive and `/compact`**, every mark is ignored, with no check of any kind (decision 9). The offer has no next round, and a mark there is not discussion that could be lost. The marks must be ignored before `parse_proposal()` checks them, not after: `asked_proposal()` gives up on any call `parse_proposal()` refuses, so a mark with `summary`, a mark with no `ref`, or one mark too many for `MAX_PARTS` would drop a valid new thought in the same call, and the discussion would be lost at archive. So both asked calls of the offer, the first one and `thought-appending`'s second one after the candidate note, get the propose tool with no `marks` property (`propose_tool_schema(..., marks=False)`), and both go through `asked_proposal()`, which calls `parse_proposal(..., offered=True)`, which skips the `marks` key whatever its shape (decision 5). A second call built with the full schema or the turn's parse would bring back the failure above at the point where it costs most: the model has just been asked again, and a malformed mark would drop the new part the candidate round was about. `asked_proposal()` keeps returning only its parts, and nothing logs an ignored mark: a mark reaches the offer only when the model ignores the schema, and no reader needs that count. When a call has no entry in `thoughts`, nothing is offered and the action goes ahead. Nothing in the offer raises for a mark, so the archive and `/compact` routes cannot fail on one, and `write_proposal()` gets no mark from the offer.

An addition part and a mark may name the same thought in one proposal. The status change does not move `updated_at` (decision 3), so confirming one never makes the other's confirm fail.

**Alternatives:** drop the bad mark in a turn too (rejected: the model would say the change is ready for review when no card shows it); show a card that fails on confirm (rejected: the user would review a change that cannot be made); refuse in the offer too (rejected: the offer has no round to correct it, so the action would fail); refuse only the first bad mark (rejected: two bad marks would take two refused rounds, past the four calls of decision 11); keep "Do not propose it" with no line about the other parts (rejected: the oat milk example above); count a refused call as the first call for layer 2's skip (rejected: a guessed ref would let a new part skip the similar-thought check); a mark-check query keyed on the id alone, with the owner checked after (rejected: a slip in the order of the checks would answer "already done" for another user's thought, and the owner filter in the query makes that impossible); check marks after layer 1 (rejected: a bad mark would cost an embedding call and a candidate round before it is refused, and could push a turn past the four calls of decision 11); log the number of marks ignored in the offer, with the conversation and proposal ids (rejected: `asked_proposal()` would have to return a count beside its parts and `offer_proposal()` a log line and a test, for a model that ignored the schema, which nothing reads); give only the first asked call of the offer the schema with no marks (rejected: the second call, after the candidate note, would then refuse a malformed mark and drop the new part it asked about); keep dropping the held note before `write_proposal()` (rejected: the example above, where the held proposal is replaced without its held part); drop it whenever `write_proposal()` returns (rejected: a candidate round returns with no proposal written, and the re-sent call would then replace the held proposal without its held parts, the same failure); log the dropped mark's title (rejected: logs hold no user content).

### 7. Confirming a status part

The confirm route, after its lock and its index checks, handles a part that has `mark`:

1. A request that names more than one part, when any is a status part, gets 422 `validation_error`: `parts: a status change is confirmed on its own`. Nothing is stored.
2. A repeated confirm finds `thought_id` set. Its early return answers `Marked done.` when the part has `mark`, and `Saved.` otherwise, with the same `thought_id`.
3. `set_status()` with the part's `mark` and `done`, before the category check. Its `not_found`, for a deleted thought or another user's, becomes 404 `not_found` with the message `This thought no longer exists.`. The body is the same in both cases, and nothing changes.
4. The part's `thought_id` is set to `mark`, and the held proposal is cleared when `unsaved_parts()` gives none (decision 9). One commit.
5. The answer is `{"saved": true, "thought_id": <mark>, "message": "Marked done."}`.

The body's title, summary, tags, category, and `mode` are ignored for a status part. A thought that is already done, for example after the user toggled it in the sheet, is confirmed with no change (decision 4, step 3). No embedding call is made, so a provider failure cannot affect it.

Setting `thought_id` keeps "this part is confirmed" in one place for a repeated confirm and the card. `saved_titles()` then gives the card the thought's current title, and `deleted` once the thought is gone, as for any saved part. Decision 8 keeps it out of the "filed" test.

**Alternatives:** a separate field such as `marked: true` instead of `thought_id` (rejected: the repeated confirm, the card, and the payload would each need a second test for "confirmed").

### 8. A status part does not count as filing

`discussion_start()` and `filed_titles()` read a part with a `thought_id` as a filed thought. A confirmed status part has one, but it filed nothing. Counted, it would move the start of the next proposal's raw text past the discussion before it, make the offer before `/compact` and archive find "nothing said since the last saved proposal" and skip that discussion, and list the marked task in `FILED_NOTE` as filed from this conversation. Example: a user talks through a podcast idea, then says "I called the plumber" and confirms only the status card; `/compact` would offer nothing, and the idea would be lost.

So only parts that filed or added to a thought, those with a `thought_id` and no `mark`, count as saved for `discussion_start()` and `filed_titles()`, and for any helper `thought-appending` adds in their place for the offer. Confirm and the card still read `thought_id` on every part (decision 7); the held proposal leaves status parts out (decision 9). The `thought-filing` delta states the rule as its own requirement, so the raw-text requirement in the main spec keeps its text. The offer requirement that `thought-appending` modifies has a scenario that the rule breaks ("Nothing said since the last saved card"), so this change modifies that requirement too, and says there what a saved proposal is (decision 15).

The next proposal's raw text then includes "I called the plumber". That is the user's own words in the discussion, and the cost of keeping the idea.

The other side of this: a conversation whose only content was "I called the plumber" and a confirmed mark now reaches the offer as unfiled discussion, and `OFFER_NOTE` asks for any task worth keeping. A model would then propose a new "Called the plumber" note at every archive and `/compact`. So `OFFER_NOTE` gains one line: `A finished task this conversation already proposed to mark done needs no new thought.` The status probe checks it (task 3.10).

**Alternatives:** count it as saved, as any part (rejected: the example above); store a confirmed status part without `thought_id` (rejected: decision 7); move `discussion_start()` past a message that held only a finished task (rejected: the server cannot tell which messages were only about the task; the model reads them, and the offer note tells it what to leave out).

### 9. A status part never holds a proposal

The held proposal exists so that unfiled discussion is not lost and the same conclusion is not proposed twice. An unconfirmed mark loses nothing: the thought exists, the card stays confirmable in the chat, and the sheet's toggle is one click away. Held like any part, a mark would be offered again on every change of topic and before every archive and `/compact`, and the next proposal ("I need oat milk") would replace it and fold its card away unless the model copied the mark into it. A mark on a thought that was later deleted, or marked done in the sheet, would also stay held for good and be re-proposed and refused on every turn.

So `unsaved_parts()` in `app/chat/prompt.py` skips parts with `mark`. Everything that decides what is held reads it:

- `held_parts()`, so a proposal whose only unsaved parts are marks is not held, and the held note never lists a mark.
- `write_proposal()`: the earlier held proposal is marked replaced only when it has an unsaved part that is not a mark. A proposal whose parts are all marks is written and shown, but does not become the held proposal and does not replace one: `conversation.held_proposal_id` stays as it was. Replacing would fold away the held proposal's unfiled parts with nothing to carry them on.
- `offer_proposal()`: returns the held proposal only when it has an unsaved part that is not a mark, and ignores every mark in both of its asked calls, the first one and the one after `thought-appending`'s candidate note (decision 6).
- Confirm clears the held proposal when `unsaved_parts()` gives none, so confirming the last new part clears it even when a mark is still unconfirmed.

On the client, `ProposalGroup` keeps a replaced proposal's status cards shown and confirmable; only its other unsaved cards fold away, and the folded count leaves marks out. The offer dialog (`proposal-dialog.tsx`) leaves status parts out: `heldProposalFor()` returns a proposal only when it has an unsaved part with no `mark`, and `onlyUnsaved` hides status cards. So the dialog's text, "This conversation has a thought you can file. Edit it and confirm, or carry on.", stays right: it never shows a status card.

**Alternatives:** hold a mark like any part, and settle one whose thought is deleted or no longer open with a `settled_marks()` query (rejected: more machinery, and a mark the user chose not to confirm is still offered again on every topic change, archive, and `/compact`, and folded away by the next proposal); a mark-only proposal replaces the held one (rejected: the held proposal's unfiled parts fold away with nothing carrying them on); hold it but word the offer dialog for a status change (rejected: it asks again about a change the user already saw and passed over).

### 10. The status card

Each proposal part in the payload (stream event, messages answer, offered proposal) gains `mark` (thought id or null). The `target` lookup from `thought-appending` reads `mark` ids too, in the same query and with the same `Thought.user_id == user.id` filter, so a crafted `mark` with another user's id gets `target: {deleted: true}` and none of that thought's fields.

`ProposalCard` shows a part with `mark` as a small card with no fields:

- Before confirm: "Mark done: <target title>", the category as a badge, and one button, "Mark done". When `target` says deleted: "This thought no longer exists." and no button.
- After confirm: "Marked done: <saved_title>" with the Open link.
- After the thought is deleted: the "Deleted" state from `thought-editing`, "Deleted: <title>" with the title stored in the part, and no Open link. The payload then gives `saved_title: null` and `deleted: true`, so the status card checks `deleted` before it reads `saved_title`, and never renders "Marked done:" with an empty title or a link to a missing thought. This holds live, when `ff:thought-changed` carries `deleted`, and after a reload.
- A 404 on confirm turns the card to "This thought no longer exists."
- Any other failed confirm (a 500, a network error, an expired demo session) shows the server's message, or the client's message when there is none, in an alert, and keeps the "Mark done" button enabled, as a new-thought card keeps its Confirm button after a refused field. The card says neither "Marked done:" nor "This thought no longer exists.", since the thought may well exist.

**The card's own name.** Each card in `ProposalCard` is a `role="group"` with its own `aria-label`: `Thought to file: <title>` before confirm and `Saved: <title>` after. A status card built in the same branches would be read as a thing to file, or as saved. So a status card is named `Mark done: <title>` before confirm and `Marked done: <title>` after, and keeps `Deleted: <title>` once the thought is gone, as any saved card does.

The group hides the merge button when any part has `mark`, as it does for `add_to`. When a later proposal replaces the group's proposal, its status cards stay shown and confirmable, and only its other unsaved cards fold away (decision 9). The offer dialog shows no status card (decision 9).

**A group with a mark is never read as merged.** `ProposalGroup` decides on load that a proposal was merged when every part has the same non-null `thought_id`. Decision 6 allows an addition part and a mark on the same thought in one proposal, and once both are confirmed both parts carry that thought's id. After a reload, or for anyone who reads the messages answer, the group would then show one merged card built by `mergeParts()`, and both the `Added to:` card and the `Marked done:` card would be gone. So the merged check holds only when no part has `mark` or `add_to`; merging is never offered for such a proposal, so it can never have been merged.

**The group's name.** The group region is named `Proposal to file` or `Proposals to file` today. A group whose parts all have `mark` is named `Proposed status change`, so a screen reader does not call a status change a thing to file. A group with any new part or addition keeps its name.

**Alternatives:** show the full thought fields, read-only (rejected: the card asks one question, and the sheet is one click away); add `status` to `target` and show "Already done" when the sheet set it first (rejected: a turn already refuses a mark on a done thought, and confirming one is a harmless no-op that ends in "Marked done"); store a `merged` flag on the proposal at a merged confirm (rejected: a new stored field and a data question for old rows, where the parts' own `mark` and `add_to` already tell the two cases apart); rename only the group region and keep the cards' names (rejected: a screen reader reads each card's own name, which would call a status change a thought to file); turn the card to "no longer exists" on any failed confirm (rejected: a 500 or a lost connection says nothing about the thought, and the card would drop its button for a thought that still exists).

### 11. Four tool rounds per turn

With three model calls, the reply needs the last one, so a turn has two rounds of tool calls. These flows need three:

- A mark on an unseen ref: propose (refused), search, propose, reply.
- `/push I called the plumber`, whose first round is forced to propose, when the model guesses a ref: propose (refused), search, propose, reply.
- "I called the plumber, and I need to buy oat milk" with an unseen plumber task and a similar oat milk thought: search, propose (candidates), propose, reply.

**Search before the first proposal.** The third flow, and any turn where an unseen finished task comes with something else to propose, works only when the model searches before its first written proposal. Once a proposal is written, `ALREADY_PROPOSED` refuses any later `propose_thought` in the turn, so a mark found by a later search is lost. The steering of task 3.10 says so: when the user says they finished a thing the conversation has not seen, search with status `open` first, then make one proposal with the mark and anything new.

A held proposal pulls the other way. `HELD_PROPOSAL_NOTE` says that on a change of topic the model's first action must be a `propose_thought` call with the held proposal. A model that follows it after "I called the plumber" proposes the held parts first, and its mark is then refused with `ALREADY_PROPOSED`; a call with only the mark is no better, since it drops the held parts and the held summary is not offered on that change of topic. This is the same whether the plumber task was filed in another conversation (not seen) or earlier in this one (seen, `T1`): in both, "I called the plumber" is a change of topic away from a held oat milk proposal. So `HELD_PROPOSAL_NOTE` gains one sentence that covers both: `If the latest message says the user finished something, make one propose_thought call that holds the held proposal and the mark; when the thing is not among the thoughts this conversation has seen, search for it with status open first.` With a seen task the flow is propose, reply: two calls. With an unseen one it is search, propose, reply: three calls, or four with a candidate round.

**A held part the user says is finished.** `/push call the plumber` is shown but not confirmed, so it is held, and the user then says "I called the plumber". No thought exists to mark. Under the sentence above, the model would search open thoughts, find nothing, propose no mark, and still make one call that holds the held proposal, so it would re-propose `Call the plumber` as a new open task, which is then offered again at archive and `/compact`. So the note gains a second sentence: `If the user says they finished something a held part is about, that part was never filed: leave it out of your next proposal, propose no mark for it, and tell the user the card was never filed and can be passed over.` When the held proposal has other parts and the turn proposes something, the new proposal holds them and replaces the held one, so the plumber card folds away. When the plumber part is the only held part, the model proposes nothing; the proposal stays held and is offered once more at archive or `/compact`, where the user passes it over (Risks).

**Several open matches.** `thought-appending` files a repeated task as new, and the migration makes every existing thought open, so a user who filed `Buy oat milk` each month has several open `Buy oat milk` tasks. "I bought the oat milk" then searches with status `open` and gets several hits, and the model could mark an old one, all of them, or any one. The steering says: when the search finds several open thoughts for the finished thing, mark only the most recently filed one, and name the older open ones in the reply, so the user can close them from the sheet. The latest filing is the one the user means by "the oat milk"; the older ones may be stale or already done and never closed, which only the user knows. The search result gives each hit's filing date, so the model can tell which is newest.

**`/push` with a finished task the conversation has not seen.** `/push` forces the first call to be `propose_thought`, so the model cannot search first. The steering says to send a mark only with a ref the conversation has seen, so a model that follows it proposes the finished thing as a new note, such as `Called the plumber`. That note goes to `thought-appending`'s layer 1, which finds the open task `Call the plumber` by its words and meaning, and the candidate round lists it by ref, with no done marker. Left alone, the model would then add to the task or file the note as new, and the task would stay open: the failure this feature exists to prevent. So `SYSTEM_PROMPT` gains one rule, backed by the `conversation-agent` requirement "A finished task among similar thoughts is marked done": when a similar-thought candidate is a thing the user says they finished, propose marking it done by that ref, and nothing new about it. A mark on a candidate needs no new ref rule, since the candidate round already gave it a ref. The flow is propose (candidate round), propose (the mark only), reply: three calls. A model that guesses a ref instead takes the refused-call flow above, in four. The status probe runs both: the forced first call, then a canned candidate round or a canned refusal, and checks the final call (task 3.10).

**`thought-appending`'s repeated-task line is qualified.** Layer 2 adds `A repeated task is usually a new task.` to the candidate round when the new part has the category `task`. In the forced `/push I called the plumber` flow the model's new note is likely to be a `task`, so its candidate round pushes the model toward `new: true`, the exact failure this flow is meant to prevent, with one `SYSTEM_PROMPT` rule as the only counterweight. So this change words the line `A repeated task is usually a new task, unless the user says they finished it.` It still steers "/push buy oat milk" a month later to a new task, as `thought-appending`'s scenario "Repeated task" asks, and costs six words, only on a candidate round with a task part. The status probe builds every canned candidate round with `thought-appending`'s own candidate-round formatter, never by hand, so it measures the line the model will really read, and runs the forced flow in a variant whose new part has the category `task` under the same 80% rule (task 3.10).

**The one flow that can need five.** A refused call does not count for layer 2's skip (decision 6). So "I called the plumber, and I need to buy oat milk", with an unseen plumber task and a similar oat milk thought, where the model guesses a ref instead of searching first, needs propose (refused), search, propose (candidates), propose, reply: five calls. `Turn.events()` runs the tool calls of its last round too, so the fourth call's proposal is written and its cards are shown; the turn then ends in `tool_loop_limit` with no reply text. The user can confirm the cards as usual. The search-first steering above makes it rare, and the status probe measures how often the model searches first (task 3.10).

`chat.yaml` `tool_rounds` goes from 3 to 4. It costs nothing on a turn that needs fewer rounds. A model that loops gets one more call before `tool_loop_limit`: at most `reply_max_tokens` more output and one more prompt on the user's key. `mcp-connectors` keeps its own `connectors.tool_rounds` (5) for conversations with a connector on.

**Alternatives:** keep 3 and let these turns end with the round-limit error (rejected: the steered path for a task the conversation has not seen would fail whenever the model first guesses a ref); a separate round budget for refused calls (rejected: a second limit in the loop for the same purpose); `tool_rounds` 5, for the guessed-ref flow above (rejected: one more call for every model that loops, on every turn, for a flow the steering avoids; `mcp-connectors` uses 5 only where connector calls need the room); let a refused call count for layer 2's skip, which keeps that flow in four (rejected: decision 6); let the held note keep "first action must be a propose_thought call" (rejected: the held proposal and an unseen finished task could not both be proposed in one turn); for `/push`, steer a forced call that has nothing seen to propose nothing new and say it will search (rejected: a forced call must hold at least one part, so "nothing" is a refused call that teaches the model nothing, and the candidate round already names the task by ref); for `/push`, let the server turn a new part whose best candidate is an open task into a mark (rejected: the server cannot tell "I called the plumber" from "call the plumber again", and the model reads the user's words); keep `thought-appending`'s repeated-task line as it is, and qualify it only if the probe's task variant fails (rejected: the line points the wrong way in exactly this flow whatever one probe run on one model measures, and a plan that waits on a probe leaves the spec undecided); a handwritten canned candidate round in the probe (rejected: it may leave out the repeated-task line, and the probe would pass on text the model never sees); a held-note sentence only for an unseen finished thing (rejected: a seen task after a held proposal hits the same `ALREADY_PROPOSED` refusal); re-propose a held part the user says is finished, or let the server drop a held proposal the model names (rejected: the first files a finished task as open, and the second is new machinery for a card the user can pass over once); mark every open match, or the oldest (rejected: every match closes tasks the user may still mean to do; the oldest is the one least likely meant).

### 12. Search: status and category filters, and a list with no query

`search_thoughts()` gains `status` and `category`. The filtered CTE gains:

```
AND (CAST(:status AS text) IS NULL OR status = :status)
AND (CAST(:category AS text) IS NULL OR category = :category)
```

`thought-dates` added a path with no query when a `dated_*` filter is given: a plain select of the filtered thoughts, no embedding call, no backfill, with a total count. This change takes the same path when `status` or `category` is given and there is no query. The list and its total both read the `filtered` CTE, which is already scoped by `user_id`, never a new plain select of `thoughts`. A search with only `status: open` is a new kind of search that lists every open thought a user has, so a check with a second user's open tasks guards that scope (task 2.1). The order is date order with a `dated_*` filter, as in `thought-dates`, and otherwise `created_at DESC`. The limit is `config.limit`.

The search tool gets `status` (enum `open` only) and `category` (a string; one of the user's categories). `search_thoughts(status=...)` stays generic and takes any stored status, so a later page such as the library can list done thoughts, but the tool offers only `open`: the feature asks that a question about open tasks leave done ones out, and that search still find done thoughts, which a search with no status does ("did I buy the oat milk?"). No scenario needs a `done` filter, and a model asked "what did I get done this week?" would pass `status: done` with the filed-date filter, since there is no filter on the done date, and miss every task filed earlier and finished this week. `parse_search()` refuses any status but `open`, `done` and `archived` alike, naming `status`, cleans the category with `clean_name()`, and refuses a call with no query and none of `dated_from`, `dated_to`, `status`, or `category`, naming `query`. A category the user does not have simply matches nothing.

The chat summary of a search with no query names its filters instead of an empty query: `Listed your` then `open` when the status is given, then `thoughts`, then ` in <category>` when a category is given, for example `Listed your open thoughts in task`; a search with only a date filter says `Listed your thoughts`. A search with a query keeps `Searched your thoughts for “<query>”`.

`format_search_result()` adds ` · <status> <date>` after the filed date of a thought whose status is not `open`, from `status_changed_at`; today that is ` · done <date>` (decision 2). An open thought gets no mark, so the usual result costs no more tokens. The model sees thoughts in three more places, and each gets the same marker: the seen-thoughts note from `thought-appending`, the candidate list of a candidate round (`thought-appending` layer 2), which lists candidates by ref, filing date, tags, and summary in its own format, and the candidate note of the offer's second asked call (`thought-appending` decision 4). Both candidate lists print each candidate line with the marker, and task 3.7 checks both; without it in the offer, the offer could propose an addition to a done task. The note is built when the turn starts, so a candidate found during the turn is not in it; without a marker in the candidate list, the model could add a new "buy oat milk" to the done task `Buy oat milk`, where the to-do would stay done and never show in an open-task search or on Upcoming. With the marker, and `thought-appending`'s line that a repeated task is usually new, it files a new task. The note's query and the candidate query read `status` and `status_changed_at` in the queries they already make. The header of a list with no query and no date filter says "newest first". With a status or category filter, the no-match text says no filed thoughts match those filters; a date-only search keeps the `thought-dates` text.

No new index. A list with no query reads the user's rows through `ix_thoughts_user_id_created_at`; at 5,000 thoughts this is well inside the `thought-search` speed budget.

**Alternatives:** an `include_done` flag that defaults to off (rejected: the user asked that search still find done thoughts, and a default that hides them would make "did I buy the milk?" answer "nothing filed"); a status filter with no category filter (rejected: every thought is open by default, so "open" alone lists ideas and notes as well; "open tasks" needs both); a separate `list_thoughts` tool (rejected: `thought-dates` already made the query optional for a filter-only search; a third tool costs tokens on every turn); a candidate-round line "If the user says they finished a candidate task, mark it done instead" (rejected: it costs tokens on every candidate round, where decision 11's six words on the existing task line cost them only on a round with a task part; the same rule sits once in `SYSTEM_PROMPT`, backed by the requirement "A finished task among similar thoughts is marked done" and measured by the status probe, decision 11); leave done candidates unmarked (rejected: the oat milk example above, and a mark on a candidate that is already done is refused and costs a round); offer `status: done` on the tool too (rejected: no scenario needs it, and the done-week question above would get a confident wrong answer; a done-date filter is a feature of its own); a boolean `open_only` instead of a one-value enum (rejected: a later value is added to the enum with no change of shape, and `status` matches the stored field and `search_thoughts()`).

### 13. The sheet's Done toggle

In view mode, the row with Edit and Delete gains a native checkbox labelled "Done" (no new dependency; the UI kit has no checkbox). Turning it sends `PATCH {status}` at once, with the box disabled while the request runs. The sheet takes the answer as its thought. A failure puts the box back and shows the server's message in an alert, as the sheet does for an edit. Beside a done box, the sheet shows "Done on <date>" from `status_changed_at`, formatted like the filed and changed dates.

The toggle is hidden in edit mode, so a status change never mixes with an unsaved edit. `thought-editing`'s "A thought opens in a side sheet" says the thought is unchanged when the user chooses neither Edit nor Delete, so this change modifies that requirement: Done joins them, with `thought-appending`'s Undo of an addition, and the sheet shows the status and the done date (decision 15). `updateThought()` dispatches `ff:thought-changed` as it does now; nothing listens for status, and the Upcoming page already reloads when the sheet closes.

**Alternatives:** status as a field in edit mode (rejected: the user asked for a toggle, and "done" is one click, not an edit); a button "Mark done" (rejected: a checkbox shows the state and the action in one control, and reads well to a screen reader).

### 14. The Upcoming page lists only open thoughts

`GET /api/thoughts/upcoming` gains `AND status = 'open'`. `thought-dates`' requirement "The Upcoming page lists dated thoughts from today on" says it lists the user's dated thoughts from today on, done or not, so this change modifies it to say open dated thoughts (decision 15). Nothing else on the page changes: it reloads when the sheet closes, so a thought marked done there drops out, and a thought set back to open comes back.

**Alternatives:** list done thoughts struck through (rejected: the page answers "what is coming up", and a done task is not).

### 15. Spec deltas and archive order

The rule: this change modifies a requirement when its text or one of its scenarios would no longer hold once this change is built, and adds a requirement when the existing text stays true and only gains a case. An open change that modifies the same requirement is not a reason to leave a broken requirement as it is: this change copies that change's version and changes it, and the copy is re-made if that version changes before archive.

Ten requirements are MODIFIED:

- `thought-search` "Filters and order" is modified by `thought-dates`, which makes the query optional with a thought-date filter and keeps the scenario "No query and no thought date", which refuses any other search with no query. An ADDED rule beside it would leave that scenario refusing a status-only search. So this change modifies the requirement: its text is `thought-dates`' text with the status and category filters added, the query optional with any of them, newest filed first without a date filter, and only the user's own thoughts listed and counted; its last scenario becomes "No query and no filter". **If `thought-dates`' version of the requirement changes before archive, re-copy it here.**
- `conversation-agent` "A proposal is held while the conversation carries on" says a proposal is held until every part is saved, is offered again on a change of topic, at archive, and at `/compact`, and that a later proposal folds its unsaved cards away. Decision 9 makes status parts an exception to all three. ### 16. Build note: the no-query list is a generalized `list_dated()`, not a read of the `filtered` CTE

### 18. Build note: where the mark check runs, and its helpers

A mark is parsed as a `ProposalPart` with `mark` set to its ref (written as the server writes refs, or the text as given when it is not a ref) and no other field; `parse_proposal()` returns the `thoughts` entries first, then one mark per ref, and `as_dict()` keeps a mark as `{"mark_ref": ...}`, as an addition keeps `add_to_ref`. The check itself is `resolve_marks()` in `app/chat/proposal.py`: the one owner-filtered query of decision 6, then `mark_refusal()`, a pure function that writes the lines and the closing line, and raises them as one `ToolRefusal`. The turn calls `resolve_marks()` right after `parse_proposal()`, before `check_parts()` (so a refused call makes no embedding call), and passes the resolved parts to `write_proposal()`; `write_proposal()` resolves only parts that still carry `mark_ref`, so a direct call (task 3.2's foreign-thought check) is checked too, and a turn's call is checked once. `mark_ids()` tells an unseen ref from a deleted thought by the refs alone: text that is not a ref, or a number past `refs.numbered`, is unseen; a deleted thought keeps its number, so its id goes to the query, which finds no row. When a refused call mixes reasons, the closing line takes the search form whenever any refused mark was unseen, and names every refused ref, the last two joined by `and` (`without T9 and T12`). The status probe reuses `mark_ids()` and `mark_refusal()`, so its canned refusals are the server's own text.

**Alternatives:** check marks only in `write_proposal()` (rejected: the turn must refuse before layer 1, which runs before `write_proposal()`); a second query on every turn's call (rejected: no need, the turn passes resolved parts).

### 19. Build note: `filed_titles()` is gone; the "filed" test is `discussion_start()` and `saved_ids()`

`thought-appending` replaced `filed_titles()` and `FILED_NOTE` with the seen-thoughts note, and the offer keeps every thought the conversation saved in it through `refs.saved_ids()`. ### 20. Build note: the held note, the summary, the offer, and confirm

### 21. Build note: the status probe

`scripts/probe_prompt.py status` runs each case of `scripts/probe_data/status.yaml` through `StatusWorld`, which answers every call as the server would: a search with `format_search_result()` and refs, a proposal's marks with `mark_ids()` and `mark_refusal()`, and a candidate round with `candidates_note()` (with the repeated-task line for a `task` part). ## Risks / Trade-offs

- [The model marks the wrong thought done] → The card names the thought by its current title, and nothing changes until the user confirms. The sheet's toggle sets it back.
- [A small model does not search before proposing, and names a ref it has not seen] → The tool result tells it to search first, and the fourth call (decision 11) leaves room to search, propose, and reply. A model that still loops ends with `tool_loop_limit`, as today. The user can still use the sheet.
- [A model says the task was marked done before the user confirms] → `PROPOSAL_SHOWN_STATUS` (decision 5) forbids it, and the status probe counts such replies against a limit.
- [A status change does not move `updated_at`, so a reader that sorts by "last changed" misses it] → `status_changed_at` is in every answer; decision 3 gives the reasons.
- [Every thought is open by default, so "open" alone lists ideas and notes] → The prompt steers the model to add the category `task` for tasks, and the status probe checks it.
- [Four calls per turn instead of three] → One more model call only for a turn that needs it or a model that loops (decision 11).
- [A model guesses a ref for an unseen finished task while the same message proposes a new thought that has a similar filed thought] → That turn needs five calls: the proposal of the fourth is shown, and the turn ends in `tool_loop_limit` with no reply (decision 11). The search-first steering and the held-note sentence make it rare, and the status probe checks that the first call is a search. The limit stays 4; the cards are still there to confirm.
- [`thought-appending` is not built, and its refs, `target`, layer 1, or `write_proposal()` may change shape] → Re-read decisions 5 to 10 before task group 3.
- [`thought-dates` is not built, and its no-query path, the Upcoming route, "Filters and order", the Upcoming list requirement, or "A proposal can be reviewed in the chat" may change] → Re-read decisions 12, 14, and 15 before tasks 2.1 and 4.4, and re-copy the three modified requirements.
- [`thought-appending` changes "A message with several thoughts is split", "Similar filed thoughts are checked", "Tools to file and find thoughts", or "The offer before an action may propose nothing", or `thought-editing` changes "A thought opens in a side sheet", before this change is archived] → Re-copy the requirement into this change's delta and re-apply this change's edit (decision 15).
- [`mcp-connectors` and this change both modify "Tools to file and find thoughts"] → Merge `mcp-connectors`' text into this change's copy before archive, and archive this change after it (decision 15).
- [`/push I called the plumber` for a task the conversation has not seen, where the forced first call files a new note and layer 1 finds no candidate, for example with no embedding key and few shared words] → The card shows a new note and the task stays open. The user sees the card before anything is stored and can pass it over; the status probe measures the forced flow (decision 11), and the sheet's toggle still closes the task.
- [The user says they finished a task whose only card is a held, unconfirmed part] → No thought exists to mark. The model proposes nothing and says the card was never filed (decision 11), so the proposal stays held and is offered once more at archive or `/compact`, where the user passes it over. When the held proposal has other parts, the next proposal replaces it and the finished card folds away.
- [Several open thoughts match a finished thing] → The model marks only the most recently filed one and names the older ones in its reply (decision 11); the user closes those from the sheet, and the status probe checks the choice.
- [`background-turns` (planned) runs the turn as a background task] → A status part is a normal proposal part in a normal proposal event; a replay shows it as it shows any card. No change needed.
- [`mcp-connectors` (planned) prefixes connector tool names and has its own round limit] → The built-in `propose_thought` and `search_thoughts` keep their names, and its `connectors.tool_rounds` (5) is already above 4.
- [`mcp-connectors` (planned) moves the search and propose code into `BuiltinTools`, which returns a `ToolOutcome`, and keeps one shared error handler in `_run_tool()`, where connector errors keep their own wording] → This change edits the same places: the `ToolRefusal` pass-through in the except clause, the held note dropped only after a proposal row is written (decision 6), the choice of `PROPOSAL_SHOWN_STATUS` and of the chat summaries in the propose and search branches (decisions 5, 6, and 12), and `details.summary` on every stored tool message (decision 5). Whichever change is built second moves the `ToolRefusal` pass-through into the shared handler, before the connector error case, and the result text and summaries into `BuiltinTools`' `ToolOutcome`. Task 3.2's check that a refusal has no suffix, and task 3.4's summary checks, guard the move.
